## 1. 这篇文档解决什么问题

很多人知道 RAG 需要：

- 文档切分
- 向量检索
- BM25
- 混合检索
- 重排

但真正落地时，问题会很快变成：

- 这些能力能不能尽量放在同一个系统里
- 表该怎么设计
- 哪些字段必须提前建好
- 查询语句怎么和表结构配合
- 怎么把它做成一个像生产系统的方案，而不是一次性 Demo

这篇文档就专门回答：

**如果你想用 Elasticsearch 落地一个真实可运行的企业 RAG 检索层，应该怎么设计。**

## 2. 适用人群

适合：

- 已经理解 RAG 基本流程，准备做工程落地的人
- 想把 `BM25 + Vector + RRF + Rerank` 放进真实系统的人
- 想知道生产级 chunk 表应该有哪些字段的人

读完后，你应该能够：

## 4. 为什么很多企业会用 Elasticsearch 做 RAG

Elasticsearch 在 RAG 里常见，不是因为它“最潮”，而是因为它同时覆盖了很多企业刚需：

- 有成熟的全文检索能力
- 默认就有 BM25
- 支持结构化过滤
- 支持聚合、统计、排序、分页
- 支持 `dense_vector` 和 kNN
- 支持 `RRF`
- 支持 `text_similarity_reranker`

对企业 RAG 来说，这意味着一件很重要的事：

**你不一定要把关键词检索、向量检索、融合和重排拆成四个分散系统。**

当然，这不代表所有东西都必须塞进 Elasticsearch。  
真实生产里更常见的是：

- 能统一的先统一
- 需要单独演进的，再拆出去

## 5. 一个真实生产级方案长什么样

一个比较稳的 Elasticsearch RAG 方案，通常长这样：

```text
原始文档
  -> 解析清洗
  -> chunk 切分
  -> 补元数据
  -> 生成 embedding
  -> 写入 Elasticsearch chunk 索引

用户 query
  -> Query 理解 / 改写
  -> BM25 检索
  -> Vector 检索
  -> RRF 融合
  -> Cross-Encoder 重排
  -> top-3 / top-5 证据送给 LLM
```

如果再更像生产系统一点，还应该补上：

- 多租户隔离
- 权限过滤
- 文档版本控制
- 删除同步
- 索引别名
- 增量重建
- 日志与评测

所以这不是一张“只是存文本”的表，而是一层真正的**知识检索基础设施**。

## 6. 生产里为什么通常按 chunk 建表

很多初学者会想：

- “我把整篇文档存进去不就好了？”

但 RAG 真正要检索的单位，通常不是整篇文档，而是 chunk。

原因很现实：

1. 大模型最终吃的是片段，不是整本手册
2. 向量检索最合适的粒度通常也是片段
3. 重排阶段需要比较的是“query 和某段内容的关系”
4. 权限、版本、标题、路径等元数据也要精确到 chunk

所以生产里更常见的设计是：

- 一篇文档拆成多个 chunk
- 每个 chunk 一条记录
- 再用 `doc_id`、`chunk_id`、`chunk_index` 把它们串起来

## 7. 一张生产级 chunk 表通常有哪些字段

下面这组字段，是企业 RAG 里比较常见的一套最小生产字段。

### 7.1 主键与定位字段

- `tenant_id`：租户 ID，多租户系统必须有
- `kb_id`：知识库 ID，同一租户下通常不止一个库
- `doc_id`：原始文档 ID
- `chunk_id`：chunk 唯一 ID
- `chunk_index`：这个 chunk 在原文中的顺序

### 7.2 检索核心字段

- `content`：chunk 正文，给 BM25 和重排使用
- `content_vector`：正文 embedding，给向量检索使用
- `doc_title`：文档标题，常常对关键词检索有帮助
- `section_title`：当前章节标题
- `section_path`：章节路径，例如 `["员工手册", "休假制度", "年假"]`

### 7.3 过滤和治理字段

- `source_type`：来源类型，例如 `pdf`、`wiki`、`faq`
- `department`：部门或业务线
- `lang`：语言
- `tags`：标签
- `doc_version`：文档版本号
- `is_latest`：是不是当前生效版本
- `is_deleted`：是否已删除

### 7.4 权限字段

- `acl_principals`：允许访问这条数据的用户组、部门、角色或主体集合

这在企业 RAG 里非常关键。  
如果没有权限字段，系统很容易“检索正确，但越权泄露”。

### 7.5 展示与调试字段

- `source_uri`：原文链接
- `published_at`：发布时间
- `updated_at`：更新时间
- `chunk_char_count`：字符数
- `chunk_token_count`：token 数
- `metadata`：保留原始元数据，方便回溯

这里有一个经验：

**生产字段不要只为“查得到”设计，还要为“排得准、控得住、查得明白”设计。**

## 8. Elasticsearch 建表语句怎么写

下面给一套接近生产实践的建表示例。

说明：

- 这是一个面向中文企业 RAG 的示例
- 下面假设你已经安装了 IK 分词器
- 如果你的集群没有 IK，可以把 `ik_max_word` / `ik_smart` 改成 `standard` 或其他可用 analyzer

### 8.1 推荐的索引命名方式

生产里通常不会直接让业务一直写死某个物理索引名，而是会配：

- 物理索引：`rag_chunks_v1`
- 读写别名：`rag_chunks_online`

这样后面你做重建、迁移、回滚会容易很多。

### 8.2 建表 DSL

```jsonc
PUT rag_chunks_v1
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1,
    "refresh_interval": "30s",
    "analysis": {
      "analyzer": {
        "rag_zh_index": {
          "type": "custom",
          "tokenizer": "ik_max_word",
          "filter": ["lowercase"]
        },
        "rag_zh_search": {
          "type": "custom",
          "tokenizer": "ik_smart",
          "filter": ["lowercase"]
        }
      }
    }
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "tenant_id": {
        "type": "keyword"
      },
      "kb_id": {
        "type": "keyword"
      },
      "doc_id": {
        "type": "keyword"
      },
      "chunk_id": {
        "type": "keyword"
      },
      "chunk_index": {
        "type": "integer"
      },
      "doc_title": {
        "type": "text",
        "analyzer": "rag_zh_index",
        "search_analyzer": "rag_zh_search",
        "fields": {
          "keyword": {
            "type": "keyword",
            "ignore_above": 256
          }
        }
      },
      "section_title": {
        "type": "text",
        "analyzer": "rag_zh_index",
        "search_analyzer": "rag_zh_search"
      },
      "section_path": {
        "type": "keyword"
      },
      "content": {
        "type": "text",
        "analyzer": "rag_zh_index",
        "search_analyzer": "rag_zh_search"
      },
      "content_vector": {
        "type": "dense_vector",
        "dims": 1024,
        "index": true,
        "similarity": "cosine"
      },
      "source_type": {
        "type": "keyword"
      },
      "source_uri": {
        "type": "keyword",
        "ignore_above": 2048
      },
      "department": {
        "type": "keyword"
      },
      "lang": {
        "type": "keyword"
      },
      "tags": {
        "type": "keyword"
      },
      "doc_version": {
        "type": "integer"
      },
      "is_latest": {
        "type": "boolean"
      },
      "is_deleted": {
        "type": "boolean"
      },
      "acl_principals": {
        "type": "keyword"
      },
      "published_at": {
        "type": "date"
      },
      "updated_at": {
        "type": "date"
      },

        "type": "integer"
      },

        "type": "integer"

        "type": "object",

      }

```

```json
POST /_aliases
{
  "actions": [
    {
      "add": {
        "index": "rag_chunks_v1",

    }

```

## 9. 文档入库时大致怎么组织

真实生产里，入库通常不是“把文档正文直接塞进去”，而是要先做离线处理。

一个 chunk 入库前通常会包含：

1. 文档解析结果
2. chunk 正文
3. chunk 对应标题层级
4. 权限信息
5. 版本信息
6. embedding

一个示例文档可以长这样：

```jsonc
POST rag_chunks_online/_doc/ch_001
{
  "tenant_id": "acme",
  "kb_id": "hr_policy",
  "doc_id": "doc_2025_leave_policy",
  "chunk_id": "doc_2025_leave_policy#003",
  "chunk_index": 3,
  "doc_title": "员工休假制度（2025版）",
  "section_title": "年假折算规则",
  "section_path": ["员工手册", "休假制度", "年假折算规则"],
  "content": "员工离职时，未休年假按照在职天数折算...",
  "content_vector": [/* 1024 维 embedding */],
  "source_type": "pdf",
  "source_uri": "https://intra.example.com/docs/leave-policy-2025",
  "department": "hr",
  "lang": "zh",
  "tags": ["假期", "制度", "年假"],
  "doc_version": 2025,
  "is_latest": true,
  "is_deleted": false,
  "acl_principals": ["all_staff", "hr_team"],
  "published_at": "2025-01-01T00:00:00Z",
  "updated_at": "2025-01-15T08:30:00Z",
  "chunk_char_count": 86,
  "chunk_token_count": 54,
  "metadata": {
    "page_no": 12,
    "source_file_name": "员工休假制度_2025.pdf"
  }
}
```

## 10. 检索链路一：全部放在 Elasticsearch 里

如果你想把：

- BM25
- Vector
- RRF
- Cross-Encoder rerank

尽量都放在 Elasticsearch 内部，那么最常见的就是 `retrievers + _search` 方案。

### 10.1 一个接近生产的查询体

```jsonc
POST /rag_chunks_online/_search
{
  "retriever": {
    "text_similarity_reranker": {
      // 最后一层：Cross-Encoder 精排
      "retriever": {
        "rrf": {
          // 中间层：RRF 融合
          "retrievers": [
            {
              "standard": {
                "query": {
                  "bool": {
                    "must": [
                      {
                        "multi_match": {
                          "query": "离职后没休完的年假怎么算",
                          "fields": ["content^3", "doc_title^2", "section_title^2"]
                        }
                      }
                    ],
                    "filter": [
                      { "term": { "tenant_id": "acme" } },
                      { "term": { "kb_id": "hr_policy" } },
                      { "term": { "is_latest": true } },
                      { "term": { "is_deleted": false } },
                      { "terms": { "acl_principals": ["all_staff", "hr_team"] } }
                    ]
                  }
                }
              }
            },
            {
              "knn": {
                "field": "content_vector",
                "query_vector": [/* query embedding */],
                "k": 50,
                "num_candidates": 200,
                "filter": {
                  "bool": {
                    "filter": [
                      { "term": { "tenant_id": "acme" } },
                      { "term": { "kb_id": "hr_policy" } },
                      { "term": { "is_latest": true } },
                      { "term": { "is_deleted": false } },
                      { "terms": { "acl_principals": ["all_staff", "hr_team"] } }
                    ]
                  }
                }
              }
            }
          ],
          "rank_window_size": 50
        }
      },
      "inference_id": "my-cross-encoder-model",
      "field": "content",
      "inference_text": "离职后没休完的年假怎么算",
      "rank_window_size": 30,
      "min_score": 0.2
    }
  },
  "size": 5
}
```

这条查询体现的是一条完整生产链路：

1. lexical 路用 `multi_match`
2. vector 路用 `knn`
3. 两路都带相同的租户、知识库、版本、删除、权限过滤
4. `RRF` 先把候选揉成一个统一池
5. `Cross-Encoder` 再做最终精排
6. 最后只返回前 5 条给上层 RAG 系统

### 10.2 这条查询最重要的不是语法，而是设计原则

你真正要学会的是下面这些原则：

- 关键词路和向量路要带相同过滤条件
- 不要把权限过滤只放在最后
- `size` 很小，但 `rank_window_size` 可以更大
- 重排前候选池通常比最终返回结果更大

## 11. 检索链路二：Elasticsearch 做前半段，Cross-Encoder 外挂

这也是非常常见的生产方案。

它的思路是：

- Elasticsearch 负责 `BM25 + Vector + RRF`
- 应用层拿到 top-20 或 top-30
- 外部模型服务做 Cross-Encoder 精排

### 11.1 为什么很多团队会这样做

因为这样更方便：

- 自己控制模型版本
- 单独做灰度和 A/B
- 自建 Hugging Face / vLLM / Triton 推理服务
- 对不同业务线接不同 reranker

### 11.2 Elasticsearch 只做前半段时的查询

```jsonc
POST /rag_chunks_online/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        {
          "standard": {
            "query": {
              "bool": {
                "must": [
                  {
                    "multi_match": {
                      "query": "离职后没休完的年假怎么算",
                      "fields": ["content^3", "doc_title^2", "section_title^2"]
                    }
                  }
                ],
                "filter": [
                  { "term": { "tenant_id": "acme" } },
                  { "term": { "kb_id": "hr_policy" } },
                  { "term": { "is_latest": true } },
                  { "term": { "is_deleted": false } },
                  { "terms": { "acl_principals": ["all_staff", "hr_team"] } }
                ]
              }
            }
          }
        },
        {
          "knn": {
            "field": "content_vector",
            "query_vector": [/* query embedding */],
            "k": 50,
            "num_candidates": 200,
            "filter": {
              "bool": {
                "filter": [
                  { "term": { "tenant_id": "acme" } },
                  { "term": { "kb_id": "hr_policy" } },
                  { "term": { "is_latest": true } },
                  { "term": { "is_deleted": false } },
                  { "terms": { "acl_principals": ["all_staff", "hr_team"] } }
                ]
              }
            }
          }
        }
      ],
      "rank_window_size": 50
    }
  },
  "size": 30
}
```

然后应用层拿这 30 条内容，调用外部 reranker 服务做精排，再把前 3 到 5 条送给 LLM。

### 11.3 什么时候更适合这种方案

更适合：

- 你已经有独立模型平台
- 需要私有化 GPU 推理
- 你们想频繁切换 reranker
- 你们希望检索系统和模型系统解耦

## 12. 生产里常见的重排模型怎么选

如果你把 Cross-Encoder 也放进 Elasticsearch 工作流里，或者把它作为外挂服务，常见模型通常有下面几类。

### 12.1 Elastic 原生能力优先

- `Elastic Rerank`
- `.jina-reranker-v3`

适合：

- 想快速跑通
- 不想先自建复杂模型推理链路
- 希望和 Elastic inference 体系结合得更顺

### 12.2 外部 API 型

- `Cohere Rerank`

适合：

- 不想自托管模型
- 更看重接入速度
- 接受外部服务依赖

### 12.3 自托管开源型

- `BAAI/bge-reranker-base`
- `BAAI/bge-reranker-v2-m3`
- `cross-encoder/ms-marco-MiniLM-L-6-v2`

大致可以这样理解：

- `bge-reranker` 系列：中文、多语言场景里更常见
- `bge-reranker-v2-m3`：更偏多语言和长文本能力
- `ms-marco-MiniLM`：英文检索里很经典，模型更轻

如果你的业务是中文企业知识库，通常会优先关注 `bge-reranker` 系列。

## 13. 上线前最该检查什么

把 Elasticsearch 方案写出来只是第一步，真正上线前，至少要检查下面几件事。

### 13.1 过滤是否一致

要确认：

- lexical 路和 vector 路的租户过滤一致
- 权限过滤一致
- 最新版本过滤一致

否则你会遇到一种很危险的问题：

**不同检索分支拿到的不是同一个候选空间。**

### 13.2 重排窗口是否过大

如果你把：

- `k`
- `num_candidates`
- `rank_window_size`
- rerank 窗口

全都拉得很大，系统很容易变得又慢又贵。

### 13.3 评测是否分层

至少要分 3 层看：

1. 召回层：top-k 是否命中
2. 重排层：top-3 / top-5 是否更准
3. 最终答案层：LLM 是否真的回答更稳

### 13.4 索引重建和回滚是否可操作

如果你没有：

- 物理索引
- 在线别名
- 可切换版本

那后面一旦要重建 embedding 或重做切分，你会很痛苦。

## 14. 常见误区

### 14.1 误区一：把 Elasticsearch 只当成“一个向量库”

这会低估它在：

- BM25
- 过滤
- 聚合
- RRF
- rerank 编排

这些方面的价值。

### 14.2 误区二：只建 `content` 和 `vector` 两个字段就够了

不够。  
真实生产里，权限、版本、标题、路径、来源、删除状态，都非常重要。

### 14.3 误区三：权限过滤可以最后再补

这很危险。  
权限应该尽量在召回阶段就生效，而不是最后展示时再挡。

### 14.4 误区四：查询语句能跑通，就算方案完整

不是。  
生产方案还要考虑索引重建、别名切换、删除同步、日志评测和失败排查。

## 15. 总结与下一步建议

如果用一句话总结这篇文章，那就是：

**生产级 Elasticsearch RAG，不是“把文本和向量存进去”这么简单，而是要把 chunk、元数据、过滤、融合、重排和治理一起设计出来。**

对很多企业来说，一个保守而靠谱的默认方案就是：

1. 按 chunk 建索引
2. 同时存 `content` 和 `content_vector`
3. 预留好租户、权限、版本、来源字段
4. 查询时走 `BM25 + Vector + RRF`
5. 再决定 Cross-Encoder 放在 ES 内还是外挂
