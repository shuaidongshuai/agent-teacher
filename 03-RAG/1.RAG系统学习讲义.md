## 1. 适用人群

这篇讲义适合已经学过 LLM 与 Prompt 基础，准备系统进入知识库问答、企业检索和 RAG 工程的人。

## 2. 学习目标

读完后，你应该能够：

1. 用自己的话解释 RAG 是什么
2. 理解 RAG 的离线链路和在线链路
3. 理解 RAG 为什么会失败，以及问题可能出在哪一层
4. 初步具备搭建最小 RAG 系统的能力

## 3. 什么是 RAG

RAG 全称是 `Retrieval-Augmented Generation`，中文通常叫“检索增强生成”。

它不是单独一个模型，而是一种应用架构。你可以把它理解成两段式流程：

1. `Retrieval`：先从资料库里检索相关内容
2. `Generation`：再把检索结果连同用户问题一起交给大模型生成答案

它适合处理这类问题：

- “根据公司制度文档，年假怎么计算？”
- “这个产品说明书里提到的电池容量是多少？”
- “请总结这 20 篇内部会议记录里关于预算的结论”

## 4. RAG 解决了什么问题

### 4.1 降低幻觉

如果没有外部资料，模型只能靠参数记忆和当前上下文回答。  
RAG 的作用是先把真实证据送到模型面前，再让它回答。

### 4.2 引入私有知识

企业最重要的信息往往不在公开互联网，而在：

- 内部 Wiki
- 产品文档
- 客服知识库
- 合同与制度文件

RAG 让模型可以“临时读取”这些知识，而不需要重新训练一个模型。

### 4.3 知识可更新

模型训练完成后，参数知识相对固定；RAG 的资料库可以持续更新。  
这让它更适合知识经常变化的业务场景。

## 5. RAG 的完整流程

可以把一个 RAG 系统理解成下面 6 步：

1. 文档收集
2. 文档预处理
3. 文档切分
4. 向量化与索引
5. 检索与重排
6. 把上下文交给模型生成答案

### 5.1 文档收集

首先要明确知识从哪里来，例如：

- Markdown
- PDF
- Word
- 网页
- 数据库记录

很多 RAG 问题不是模型问题，而是源数据问题。

### 5.2 文档预处理

在真正做检索之前，通常要做：

- 去除无意义页眉页脚
- 修正文档编码问题
- 标记标题层级
- 识别表格、代码块、列表
- 给文档补充元数据

### 5.3 文档切分

长文档不能无限塞进上下文，所以要切成更小的 `chunk`。

切分的目标不是越小越好，而是：

- 粒度足够细
- 信息仍然完整
- 成本和精度平衡

### 5.4 向量化与索引

切分后的文本通常会被转成 embedding，并和原文、元数据一起存入索引系统。

### 5.5 检索与重排

用户提问后，系统先做检索，而不是直接回答。  
真实系统里更常见的方案是：

**混合检索 = 关键词检索 + 向量检索**

你可以先建立一个非常实用的判断：

- 关键词检索更擅长“字面命中”
- 向量检索更擅长“语义相似”
- 混合检索更适合生产环境里的大多数真实问题

很多初学者会以为，做了 embedding 之后就应该完全依赖向量检索。  
但真实 RAG 往往不会只用一种检索方式，因为用户问题和文档形态差异很大。

### 5.5.1 RAG 一般如何进行检索

一个常见的线上检索链路可以理解成下面几步：

1. 先理解用户问题
2. 决定检索策略
3. 分别召回候选
4. 合并候选结果
5. 重排后再交给模型

更具体一点：

1. 用户提问后，系统先做 query 理解，例如实体提取、时间范围识别、术语归一
2. 如果问题里有明确关键词、编号、专有名词，通常会保留一条关键词检索链路
3. 如果问题更口语化、更像自然表达，通常会走向量检索，找语义相近的片段
4. 如果希望兼顾覆盖率和稳定性，就把两路结果合并，这就是混合检索
5. 合并后的候选一般不会直接送给模型，而是再做一轮 rerank，把最像答案证据的内容排到前面

所以从工程视角看，RAG 的检索通常不是“用户一句话 -> 查一次向量库 -> 结束”，而是：

**Query 理解 -> 关键词召回 / 向量召回 -> 合并 -> 重排 -> 生成**

### 5.5.2 关键词检索适合什么问题

关键词检索更适合下面这类场景：

- 问题里有准确术语、产品名、组织名、接口名
- 问题里有编号、版本号、错误码、日期、章节名
- 文档本身就是制度、合同、FAQ、参数表这类强关键词材料

例如：

- “P8 职级晋升条件是什么？”
- “报销制度 2025 版里，差旅住宿标准是多少？”
- “接口 `CreateOrder` 的超时错误码是什么意思？”

这类问题的关键不在“语义像不像”，而在“字面是否命中”。  
如果文档里明明写的是 `P8`、`CreateOrder`、`ERR_1042`，只靠向量检索有时反而不稳定。

### 5.5.3 向量检索适合什么问题

向量检索更适合下面这类场景：

- 用户问得比较口语化
- 用户没有使用文档里的原始措辞
- 问题强调“意思相近”，而不是“字面相同”

例如文档写的是“员工离职时未休年假折算规则”，用户可能问：

- “离职后没休完的年假怎么算？”

这时关键词不一定完全一致，但语义很接近，向量检索通常更容易把相关 chunk 找出来。

### 5.5.4 为什么生产里经常要做混合检索

混合检索的核心原因很简单：

**现实问题既有“字面约束”，也有“语义约束”。**

只做关键词检索，容易漏掉表达不同但意思相同的内容。  
只做向量检索，又容易把“方向差不多但细节不对”的片段召回上来。

所以很多生产系统会采用这类策略：

1. 用 BM25 或其他关键词方案召回一批候选
2. 用向量检索再召回一批候选
3. 对结果去重、合并
4. 用 reranker 做统一排序

这样做的好处是：

- 对专有名词、编号、版本号更稳
- 对口语化提问和改写表达也有覆盖
- 更适合企业文档里“结构化术语 + 自然语言描述”混杂的情况

### 5.5.5 BM25 是什么

如果你在 RAG 里看到 BM25，可以先把它理解成：

**一种非常经典的关键词相关性排序算法。**

它可以看作是在传统 `TF-IDF` 思路上继续发展出来的更实用版本。  
如果只抓住一个重点，那就是：

**BM25 不是只看“词有没有出现”，而是在综合判断“出现了多少次、这个词稀不稀缺、这篇文档是不是太长”。**

它的目标不是理解深层语义，而是判断：

- query 里的词有没有出现在文档里
- 出现了多少次
- 这些词是不是这个文档里比较有区分度的词
- 文档长度会不会影响匹配分数

直觉上，你可以把 BM25 理解成“比简单关键词匹配更聪明一点的打分器”。

它通常比“只要包含关键词就算命中”的布尔检索更实用，因为它会给不同文档打分，区分“只是提到一下”和“非常相关”。

在 RAG 场景里，BM25 常见价值是：

- 强化专有名词命中
- 强化数字、版本号、错误码、接口名命中
- 给混合检索提供一条稳定的关键词召回链路

你也可以把 BM25 进一步拆成 3 个核心因子理解。

#### 5.5.5.1 TF：词频，但不是无限线性加分

`TF` 是 `Term Frequency`，也就是某个词在当前文档里出现了多少次。

直觉上，一个搜索词在文档里出现次数越多，这篇文档往往越相关。  
但 BM25 和早期一些更朴素的 TF-IDF 用法不同，它不会让词频一直线性暴涨。

BM25 引入了一个非常重要的思想：

**词频饱和。**

例如：

- 一篇文档出现 3 次 “Java”，通常明显比只出现 1 次更相关
- 但出现 100 次和出现 101 次，相关性通常不会有本质差别

这比简单的“出现越多分越高”更符合真实搜索场景。

#### 5.5.5.2 IDF：越稀缺的词，区分能力越强

`IDF` 是 `Inverse Document Frequency`，中文通常叫逆文档频率。

它要解决的问题是：

- 如果一个词在几乎所有文档里都出现，那它就没什么区分力
- 如果一个词只出现在少量文档里，那它往往更关键

例如“的”“什么是”“以及”这类常见词，几乎不能帮助你区分文档；  
而产品名、疾病名、接口名、组织名、错误码、专业术语，通常更有检索价值。

所以 IDF 的作用可以概括成一句话：

**调低常见词权重，拉高稀缺词权重。**

#### 5.5.5.3 文档长度：长文档不会天然占便宜

BM25 还会考虑文档长度。

直觉上，在一段很短的文本里出现某个关键词，往往说明它更聚焦；  
而在一篇上万字长文里只出现一次同样的词，相关性未必就高。

所以 BM25 会对过长文档做一定程度的长度归一化。  
你可以把它粗略理解成：

**避免长文因为“词更多、机会更多”而天然占便宜。**

#### 5.5.5.4 BM25 公式不用硬背，但最好看懂它在表达什么

如果你对底层逻辑感兴趣，可以看一个简化表达：

```text
Score(D, q) = IDF(q) * [ f(q, D) * (k1 + 1) ] 
              / [ f(q, D) + k1 * (1 - b + b * |D| / avgdl) ]
```

其中：

- `f(q, D)` 表示词 `q` 在文档 `D` 中出现的次数
- `|D| / avgdl` 表示当前文档长度和平均文档长度的对比
- `k1` 控制词频饱和得有多快
- `b` 控制文档长度惩罚得有多强

这套公式你不需要背下来，但最好知道它在表达什么：

- 词出现得更多，通常加分
- 但这个加分会逐渐饱和
- 文档过长时，会被适度拉低分数
- 稀缺词比常见词更值钱

#### 5.5.5.5 在 Elasticsearch 里，`k1` 和 `b` 是常见调节点

如果你在 Elasticsearch 里看 BM25 配置，最常见的两个参数就是 `k1` 和 `b`。

- `k1` 越小，词频带来的加分越快见顶
- `k1` 越大，词频的影响会持续更久
- `b` 越接近 `0`，越不考虑文档长度
- `b` 越接近 `1`，越强调长度归一化

对教学理解来说，你只需要知道：

- `k1` 在调“词频有多重要”
- `b` 在调“文档长度影响有多大”

生产里确实可以调它们，但对初学者来说，先理解“为什么要有这两个旋钮”比记默认值更重要。

### 5.5.6 Elasticsearch 中是否使用 BM25

会，而且非常常见。

如果你使用 Elasticsearch 做全文检索，那么默认相关性排序里通常就会涉及 BM25。  
也就是说，很多基于 Elasticsearch 的关键词检索，本质上就是在使用 BM25 或以 BM25 为核心的相关性打分机制。

所以工程上常见的组合是：

- Elasticsearch 负责关键词检索、倒排索引、过滤和聚合
- 向量数据库或 Elasticsearch 的向量能力负责语义检索
- 上层再做混合召回与重排

换句话说：

- “BM25 是什么”是算法层问题
- “Elasticsearch 是否使用 BM25”是工程实现层问题

两者并不冲突。很多团队说“我们用 ES 做关键词检索”，背后实际就是在用 BM25 这一套思路。

如果你以后需要深入做 ES 调优，也可以进一步关注：

- 不同字段是否用同一套相似度配置
- 标题、正文、标签是否应该有不同权重
- 是否需要结合过滤、boost、短语匹配一起使用

但对这份 RAG 入门讲义来说，先理解“ES 常把 BM25 用作关键词相关性基础”就够了。

### 5.5.7 一个常见的生产级检索思路

如果你不知道 RAG 检索该怎么设计，可以先从一个保守而实用的默认方案开始：

1. 文档切分后，同时建立向量索引和关键词索引
2. 查询时先做 query 改写和元数据过滤
3. 用 BM25 召回 top-k
4. 用向量检索再召回 top-k
5. 合并去重
6. 用 reranker 选出最值得放进上下文的若干条
7. 最后再交给大模型回答，并尽量带出处

这个方案不是唯一正确答案，但它是很多企业 RAG 的常见起点。  
原因不是它最炫，而是它更稳定、更容易排查问题，也更符合真实文档场景。

之后再用重排模型对候选结果排序。

### 5.6 生成答案

最终模型不是“凭空回答”，而是基于检索证据组织答案。  
因此最终答案质量，依赖于上游证据是否相关、完整、排序合理。

## 6. 你可以怎样理解 RAG 的本质

一个非常实用的理解方式是：

**RAG 不是问答技巧，而是信息供给系统。**

很多看起来像“模型不聪明”的问题，本质上其实是：

- 没找对资料
- 找出来的资料不完整
- 排序不对
- 查询没被系统正确理解

## 7. RAG 的几个关键模块

建议把 RAG 拆成下面 5 个模块理解：

1. 数据层：文档质量、清洗、结构恢复
2. 索引层：切分、向量化、元数据组织
3. 检索层：关键词、向量、混合召回
4. 排序层：rerank、候选筛选
5. 生成层：上下文组织、答案生成、引用出处

## 8. RAG 为什么会失败

最常见的失败原因有：

1. 数据源本身就脏
2. 切分把关键信息切断了
3. 查询没有被正确理解
4. 召回候选里缺了关键证据
5. 重排顺序不合理
6. 给模型的上下文太长或太乱

## 9. RAG 的常见优化方向

真实优化通常围绕下面几个方向：

1. 数据清洗和结构恢复
2. 切分策略调整
3. Embedding 模型选型
4. 混合检索
5. 重排模型
6. Query 改写与检索路由
7. 答案模板与引用策略

## 10. 一个最小可行 RAG 系统长什么样

一个最小版本通常包括：

1. 一批清洗过的文档
2. 基础切分逻辑
3. 一个 embedding 模型
4. 一个向量索引
5. 一个把检索结果送给模型的问答接口

不要一开始就追求最复杂框架。  
真正重要的是：链路可解释、问题可定位。

## 11. 学习 RAG 时最该关注的指标

建议优先关注：

1. 是否召回了该找的资料
2. 候选排序是否合理
3. 最终答案是否忠于证据
4. 是否能给出稳定出处

## 12. RAG 与微调的区别

一个很实用的区分是：

- RAG 解决“怎么把外部知识送进去”
- 微调更偏“怎么改变模型行为模式”

如果问题是知识更新快、知识在外部文档里，通常先考虑 RAG。  
如果问题是输出风格、领域任务模式、行为一致性，则可能考虑微调。

## 13. 初学者常见误区

- 把 RAG 当成“向量库 + Prompt”
- 只盯着生成层，不看上游证据
- 看到效果差就只想换更强模型
- 忽视数据清洗和元数据设计

## 14. 自学练习题

### 练习 1

为什么说很多 RAG 问题不是模型问题，而是数据或检索问题？

思考方向：

- 模型看到的证据是否正确
- 关键资料是否根本没有被送到模型面前

### 练习 2

切分为什么既不能太小，也不能太大？

思考方向：

- 太小会丢上下文
- 太大则会稀释相关信息并浪费窗口

### 练习 3

如果用户问“去年研发投入变化和利润趋势是否一致”，你觉得这是更像召回问题、排序问题还是查询理解问题？

思考方向：

- 是否涉及时间范围
- 是否涉及多指标和比较关系

## 15. 总结与下一步建议

这篇讲义最重要的一句话是：

**RAG 的本质，不是让模型“更聪明”，而是让系统更稳定地给模型提供正确证据。**
