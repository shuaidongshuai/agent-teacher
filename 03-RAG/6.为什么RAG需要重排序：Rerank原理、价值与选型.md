## 1. 这篇文档回答什么问题

很多人第一次做 RAG 会问：

“既然已经检索出了 top-k 文档，为什么还要再排一次？”

答案是：

**因为召回擅长的是从大规模资料里先找出候选，而不一定擅长把最相关的那几个稳定排在最前面。**

而最终进入大模型上下文的内容通常很少，所以前几名排得对不对，影响非常大。

---

## 2. 为什么只有召回还不够

### 2.1 召回强调覆盖，不一定强调精排

无论是 BM25、向量检索还是混合检索，很多时候目标都是：

- 尽量别漏掉相关内容
- 先从海量文档中缩小范围

这一步更像“海选”。

但海选后的前 20 条里，经常会混入：

- 主题相关但不回答当前问题的内容
- 同一主题下的旧版本文档
- 只匹配了关键词、但语义不够贴合的片段

### 2.2 生成模型的上下文预算有限

你不可能把 top-50 全塞给大模型。通常真正送进去的只有很少几个 chunk。

所以问题变成：

**不是“有没有找出来”，而是“最该给模型看的那几个，是否排在最前面”。**

---

## 3. 重排序到底在做什么

重排序的输入通常是：

- 用户 query
- 召回阶段拿到的一批候选 chunk

输出则是：

- 每个候选与 query 的更精细相关度分数
- 重排后的候选顺序

你可以把它理解成两层机制：

1. 召回层负责快速缩小搜索空间
2. 重排层负责更精细地理解“这个 query 到底最想问什么”

在直觉上，重排模型比普通召回更像在做“成对判断”：

- 这个问题和这段文本是否真正匹配
- 这段文本是否能支撑回答
- 这段文本是否只是主题接近，但并未回答关键条件

---

## 4. 为什么它对最终答案影响很大

### 4.1 前几名质量决定上下文质量

生成模型看到的不是整个知识库，而是少量被筛选出来的上下文。

如果前 3 条资料刚好最相关，答案往往很稳。

如果前 3 条资料里混入了：

- 旧政策
- 旁支主题
- 条件不完整的段落

模型就可能被误导。

### 4.2 它能缓解“相似但不相同”的问题

企业检索里非常常见的情况是：

- 同一个制度里有多个相近条款
- 同一产品线有多个版本
- 问题里只差一个时间范围、地区或员工级别

粗召回可能都找得到，但排序顺序未必稳定。重排就在这里补上最后一公里。

---

## 5. 哪些场景尤其需要重排序

下面几类场景，通常更建议加 Rerank：

### 5.1 文档很多，主题接近

例如制度库、产品手册、客服知识库，常常有大量近似文本。

### 5.2 用户问题包含条件约束

例如：

- 适用于上海地区吗
- 2025 年版本怎么规定
- 对 P7 以上员工是否生效

这类问题里，单纯语义相近不够，需要更细地判断条件是否满足。

### 5.3 top-k 候选能覆盖答案，但最终答案仍然不稳

这是一个很典型信号：

候选已经有了，但排序不够好。

---

## 6. Rerank 模型怎么选

选型时建议重点看下面几个维度：

### 6.1 语言与领域适配

如果你的知识库以中文为主，就优先关注中文 query 和中文 chunk 的匹配效果。

### 6.2 延迟

重排序通常发生在用户查询链路上，所以比离线 Embedding 更受延迟影响。

### 6.3 候选规模

如果每次都要对 100 个候选做重排，代价会明显高于只排前 20 个。

### 6.4 与召回模块的配合

有些 Rerank 模型并不是单独看最强，而是和你的召回方式、chunk 粒度、query 形式配合后整体更好。

### 6.5 部署方式

和 Embedding 一样，也要考虑：

- 是否能私有化
- 是否满足数据合规要求
- 是否支持你的流量规模

### 6.6 不同方案，不是在同一层打架

很多人会把下面两个问题混在一起：

- “混合检索之后要不要做结果融合？”
- “融合之后要不要再上深度重排模型？”

它们其实不是同一个层级的问题。

一个更清晰的理解方式是：

1. 多路召回之后，先想办法把结果合成一个更稳定的候选列表
2. 候选列表缩小后，再决定要不要用更重的模型做精排

也就是说，`RRF` 更像是**融合 / 粗排**，而 `Cross-Encoder` 更像是**精排 / 深排**。

### 6.7 混合检索后，通常仍然建议重排

如果你的系统已经在做：

- `BM25` 关键词检索
- 向量检索
- 两路或多路召回合并

那通常还不算结束。

原因是：

- BM25 擅长字面命中，但不一定最懂整句语义
- 向量检索擅长语义相似，但也可能把“方向接近但条件不对”的片段召回上来
- 两路结果即使合并了，也只是说明“候选范围更全了”，不等于“前几名一定最适合回答”

所以混合检索解决的更多是**覆盖率问题**，而重排解决的更多是**前几名精度问题**。

如果最终只允许给大模型喂 3 到 8 条证据，那么“前几名排得对不对”往往比“后面 50 条有没有找到”更重要。

---

## 7. 混合检索之后为什么还要再重排

可以把双路召回理解成一次“扩充候选池”的过程。

例如：

1. BM25 召回 top-100
2. 向量检索召回 top-100
3. 合并、去重后得到几十到上百条候选

这时候系统只是更有机会“把正确答案包含进来”，还没有保证：

- 最关键证据排在最前面
- 旧版本文档不会混进高位
- 只匹配了关键词、但不真正回答问题的片段不会抢前排
- 条件约束更完整的 chunk 能稳定压过泛泛而谈的 chunk

所以从工程角度看：

**混合检索更像“先别漏”，重排更像“别排错”。**

对 RAG 来说，这一步尤其重要，因为大模型不是看完整个候选池，而是只看最前面的少量证据。

---

## 8. RRF 和 Cross-Encoder 有什么区别

在双路召回架构里，`RRF` 和 `Cross-Encoder` 都可能出现在“重排”这一层，但它们做的事情其实很不一样。

### 8.1 RRF 是什么

`RRF` 全称是 `Reciprocal Rank Fusion`，常翻成倒数排名融合。

它本质上不是深度学习模型，而是一种基于排名位置的融合算法。  
它不关心文档原始文本内容，也不强依赖不同召回器给出的原始分数是否可比较。

它更关心的是：

- 这条结果在 BM25 里排第几
- 这条结果在向量检索里排第几
- 是否在多路召回中都排得比较靠前

直觉上，RRF 像一种“投票机制”：

- 如果一条文档在多路召回里都排得不错，它最终排名通常会更高
- 如果它只在某一路偶然冲得很高，而在其他路完全没出现，最终优势就没那么大

### 8.2 Cross-Encoder 是什么

`Cross-Encoder` 则完全不同。

它通常是一个深度学习重排模型，会把 `query` 和 `document` 放在一起做联合编码，然后直接判断：

- 这段文本和这个问题到底有多匹配
- 它是不是能真正回答这个问题
- 它是不是只是主题接近，但条件不满足

所以它比 RRF 更像在做“逐条审阅”。

RRF 看的是“排名信号怎么合并”；  
Cross-Encoder 看的是“这条文本和这个问题本身到底匹不匹配”。

### 8.3 两者的核心区别

你可以先记住这张对比表：

| 维度        | RRF       | Cross-Encoder           |
| --------- | --------- | ----------------------- |
| 本质        | 基于排名的融合算法 | 深度学习重排模型                |
| 输入        | 多路召回的排名结果 | `(query, document)` 文本对 |
| 是否读取文本内容  | 否         | 是                       |
| 是否需要训练    | 不需要       | 通常需要现成模型，领域内常希望进一步适配    |
| 计算代价      | 很低        | 明显更高                    |
| 适合处理的候选规模 | 大一些也可以    | 通常只适合较小候选集              |
| 更适合放在哪一层  | 融合 / 粗排   | 精排 / 深排                 |

### 8.4 什么时候更偏向用 RRF

下面这些场景，通常更适合先用 RRF：

- 系统时延预算紧
- 没有 GPU 或 GPU 很贵
- 项目冷启动，暂时没有精细调优条件
- 你需要先把 BM25 和向量检索稳定地揉成一个统一候选池

RRF 的优点是：

- 实现简单
- 不依赖训练数据
- 不依赖复杂模型部署
- 作为基线通常比较稳，不容易完全翻车

它特别适合做第一道融合，把多路检索结果先压成一个还不错的候选列表。

### 8.5 什么时候更偏向用 Cross-Encoder

下面这些场景，通常更值得引入 Cross-Encoder：

- 你很在意 top-1 或 top-3 的准确率
- 用户最终只看极少数结果
- query 有复杂条件、否定关系、范围约束
- 文本之间很像，粗排很难稳定区分

例如用户问：

- “如何不花钱坐地铁”

这类 query 里，否定词、合规边界、真实意图都很重要。  
单靠关键词命中或者向量相近，可能会把一些字面接近但语义不合规的内容排得过高。Cross-Encoder 往往更擅长处理这种“整句真正想表达什么”的问题。

### 8.6 它们不是二选一，而是前后配合

工业界更常见的思路不是：

- “RRF 和 Cross-Encoder 选一个”

而是：

- “先用 RRF 做融合和粗排，再用 Cross-Encoder 做精排”

原因很简单：

- 让 Cross-Encoder 去看几百条候选，通常太贵、太慢
- 先用 RRF 这种轻量方法把候选缩到 20 到 50 条，再做深度精排，会更平衡

## 9. 生产里常见的重排架构怎么搭

一个很常见的生产级漏斗可以这样理解：

```text
用户 Query
   -> BM25 召回 top-N
   -> 向量召回 top-N
   -> RRF 融合与去重
   -> 得到统一候选池 top-M
   -> Cross-Encoder 精排
   -> 选出最终 top-K
   -> 送入大模型生成答案
```

如果写得更工程一点，就是：

1. BM25 负责抓强关键词、术语、编号、版本号
2. 向量检索负责补语义相似、口语化表达和改写表达
3. RRF 负责把多路结果快速融合成统一列表
4. Cross-Encoder 负责在较小候选池里做更精细的相关性判断
5. 最终只把最值得信任的少量证据交给 LLM

### 9.1 为什么这是常见默认方案

因为它在“性能”和“效果”之间比较平衡：

- 不会一开始就让重模型扫描所有候选
- 也不会只靠轻量融合就结束，导致前几名不够稳
- 它既利用了多路召回的覆盖能力，也利用了深度重排的精度能力

### 9.2 如果资源有限，怎么做取舍

你可以用一个很实用的顺序来判断：

1. 先把混合检索跑通
2. 再加 RRF 或其他轻量融合
3. 确认召回覆盖率和粗排已经比较稳定
4. 如果 top-1 / top-3 仍然不稳，再引入 Cross-Encoder

对很多团队来说，正确顺序不是“上来就最强模型拉满”，而是：

**先把候选池做对，再把前几名做准。**

## 10. 生产级实践：Elasticsearch 如何接入整条链路

这一节回答的不是某一个单点，而是一个更完整的问题：

**Elasticsearch 到底能覆盖 RAG 检索链路里的哪些环节？哪些环节可以直接放进 ES，哪些环节也可以自己单独实现？**

如果只看这一段检索链路，通常会涉及：

1. `BM25` 关键词召回
2. `Vector` 语义召回
3. `RRF` 融合
4. `Cross-Encoder` 精排

从官方能力看，Elasticsearch 已经支持把这几层中的大部分甚至全部收进同一条检索工作流里。

### 10.1 Elasticsearch 能覆盖哪些步骤

在当前 Elasticsearch 官方能力里，至少已经明确支持：

- 关键词检索
- kNN / dense vector 检索
- `RRF` 融合
- rerank

而且官方给出了两种组织方式：

1. 用 `retrievers` 在单次 `_search` 请求里组织多阶段检索
2. 用 `ES|QL` 的 `FORK`、`FUSE`、`RERANK` 串起多路检索和重排

这意味着它不只是一个“向量库外加 BM25”的组件，而是已经能承担很大一部分检索编排工作。

这里最好再区分清楚：

- `retrievers` 是 **`_search` 接口下的 Query DSL / JSON 写法**
- `ES|QL` 是 **`_query` 接口下的管道式查询语言**

所以它们可以理解成：

- 都能做多阶段检索
- 但属于 **两套不同的查询接口**

而这份文档前面给出的示例，使用的是第一种，也就是：

- `retrievers + _search`

### 10.2 接入模式一：整条链路尽量放进 Elasticsearch

如果写成更具体的链路，就是：

```text
用户 query
  -> Elasticsearch 标准检索（BM25）
  -> Elasticsearch kNN / dense vector 检索
  -> Elasticsearch RRF 融合
  -> 得到统一候选 top-20 / top-50
  -> Cross-Encoder rerank
  -> 最终 top-3 / top-5 送给 LLM
```

这个链路的好处是职责很清楚：

- `BM25` 负责专有名词、编号、版本号、术语
- `Vector` 负责语义相似、口语化表达、改写表达
- `RRF` 负责把两路结果快速揉成一个统一候选池
- `Cross-Encoder` 负责最后的精细判别

这种模式的核心特征是：

- 检索逻辑集中在 ES
- 应用层少做结果拼装
- DSL 直接表达“召回 -> 融合 -> 精排”

一个很接近生产实践的检索体，可以写成下面这样：

```jsonc
POST /my_rag_index/_search
{
  "retriever": {
    "text_similarity_reranker": {
      // 外层 reranker：对已经召回的候选做 Cross-Encoder 精排
      "retriever": {
        "rrf": {
          // RRF：先把 BM25 和向量检索的结果融合成统一候选池
          "retrievers": [
            {
              "standard": {
                "query": {
                  "match": {
                    // BM25 检索文本
                    "content": "如何开通Stripe"
                  }
                }
              }
            },
            {
              "knn": {
                // 向量字段
                "field": "vector",
                // query 的 embedding
                "query_vector": [/* query embedding */],
                // 最终从向量检索返回多少条结果参与融合
                "k": 100,
                // ANN 近似检索时，先考察多少候选点；越大通常越准，但越慢
                "num_candidates": 200
              }
            }
          ],
          // RRF 融合阶段，每一路最多取前 50 条参与融合
          "rank_window_size": 50
        }
      },
      // 指向一个 rerank 类型的 inference endpoint
      "inference_id": "my-cross-encoder-model",
      // 用哪个文本字段参与 Cross-Encoder 相似度判断
      "field": "content",
      // 重排时真正拿来和候选文本做匹配的 query 文本
      "inference_text": "如何开通Stripe",
      // 融合完成后，最多取前 50 条送去 Cross-Encoder 精排
      "rank_window_size": 50,
      // 低于这个分数的候选直接过滤掉
      "min_score": 0.6
    }
  }
}
```

这段 DSL 表达的就是：

1. 先用 `standard` 跑 BM25 文本检索
2. 再用 `knn` 跑向量召回
3. 用 `RRF` 把两路结果融合
4. 把融合后的前 `50` 条送给 `text_similarity_reranker`
5. 用 `Cross-Encoder` 模型做最终精排
6. 用 `min_score` 过滤掉重排分数太低的结果

要注意几个容易写错的点：

- `text_similarity_reranker` 里必须提供 `inference_text`
- `RRF` 用的是 `rank_window_size`，不是 `window_size`
- reranker 自己也有一个 `rank_window_size`，表示送去精排的候选数量
- `inference_id` 指向的是一个 `rerank` 类型的 inference endpoint，不只是任意模型名

所以如果你问“这是不是就代表 Elasticsearch 已经把 Cross-Encoder 集成进来了”，答案是：

**是的，从检索链路编排角度看，Elasticsearch 已经支持把 Cross-Encoder rerank 作为 retriever 链的一部分接进去。**

### 10.2.1 如果换成 ES|QL，通常怎么写

如果你想用第二种方式，也就是 `ES|QL`，思路上会从“嵌套 JSON”变成“管道拼接”。

可以先把它理解成下面这种形态：

```text
FROM index
| FORK (
    ... 一路做 BM25 / MATCH ...,
    ... 一路做语义检索 / KNN ...
  )
| FUSE
| RERANK
```

一个教学化、接近文档语义的例子可以写成：

```sql
FROM my_rag_index
| LIMIT 0
| FORK
  (
    FROM my_rag_index
    | WHERE MATCH(content, "如何开通Stripe")
    | KEEP _id, content
    | LIMIT 50
  ),
  (
    FROM my_rag_index
    | WHERE KNN(vector, [/* query embedding */], 100)
    | KEEP _id, content
    | LIMIT 50
  )
| FUSE
| RERANK "如何开通Stripe" ON content
  WITH (
    inference_id = "my-cross-encoder-model",
    rank_window_size = 50,
    min_score = 0.6
  )
| LIMIT 5
```

这段 ES|QL 表达的意思，和前面的 `retrievers` 版本是一致的：

1. 一路做 `MATCH`
2. 一路做 `KNN`
3. 用 `FUSE` 合并多路结果
4. 用 `RERANK` 调 Cross-Encoder 精排
5. 最后只保留前几条高质量证据

### 10.3 接入模式二：Elasticsearch 只接前半段，Cross-Encoder 自定义

这也是业界非常常见的一种模式。

链路通常会写成：

```text
用户 query
  -> Elasticsearch BM25
  -> Elasticsearch Vector
  -> Elasticsearch RRF
  -> 应用层拿到 top-N 候选
  -> 外部 Cross-Encoder 服务精排
  -> 最终 top-K 送给 LLM
```

这种模式适合下面几类团队：

- 希望自己控制模型服务
- 需要私有化部署
- 想灵活切换不同 reranker
- 想单独做灰度、A/B 和版本管理

它的优势是：

- rerank 模型独立演进更方便
- 更容易接入 Hugging Face、vLLM、Triton、自建推理服务
- 便于按业务线分别使用不同重排模型

它的代价是：

- 应用层要多承担一段编排逻辑
- 需要自己处理模型服务的超时、重试、扩容和监控

所以更准确的说法不是：

- “Elasticsearch 只能做前半段”

而是：

- “Elasticsearch 已经能做整条链路，但很多团队仍会只用它做前半段，把 Cross-Encoder 留给自定义模型服务。”

### 10.4 这些参数在生产里一般怎么取

上面这个请求体里，最容易让人拿不准的通常是 4 个参数：

- `k`
- `num_candidates`
- `rrf.rank_window_size`
- `text_similarity_reranker.rank_window_size`

你可以先这样理解它们分别在控制什么。

#### `k`：向量检索最终要吐出多少条结果

`k` 控制的是：

**kNN 这一支，最后返回多少条文档参与后续融合。**

如果 `k` 太小：

- 向量检索这一路的覆盖率可能不够
- 很多本来应该进入混合候选池的文档进不来

如果 `k` 太大：

- 候选噪声会增多
- 后面的融合和重排成本会增加

一个常见起点是：

- 小型知识库：`20 ~ 50`
- 中大型知识库：`50 ~ 100`

如果你已经知道问题通常比较复杂、表达比较口语化，可以适当把 `k` 往上提一点。

#### `num_candidates`：向量检索先粗看多少候选点

`num_candidates` 控制的是：

**近似向量检索阶段，底层先探索多少候选，再从里面选出 top-k。**

它不直接等于最终返回条数，但会影响向量召回质量。

一般规律是：

- `num_candidates` 越大，向量召回通常越稳
- 但延迟和计算成本也会上去

实践里，经常把它设成 `k` 的几倍。一个保守起点可以是：

- `num_candidates = 2x ~ 5x k`

例如：

- `k = 50`，可以先试 `num_candidates = 100 ~ 250`
- `k = 100`，可以先试 `num_candidates = 200 ~ 500`

#### `rrf.rank_window_size`：每一路检索最多拿多少条进 RRF

这个参数控制的是：

**BM25 路和向量路，各自最多拿前多少条结果参与 RRF 融合。**

它本质上影响的是融合阶段的候选池宽度。

如果这个值太小：

- 融合候选池可能不够丰富
- 多路召回的互补价值发挥不出来

如果这个值太大：

- 候选噪声增多
- 后续精排压力变大

常见经验是：

- 先从 `30 ~ 100` 开始试
- 大多数 RAG 场景里，`50` 是一个比较稳的起点

#### `text_similarity_reranker.rank_window_size`：最终送去 Cross-Encoder 精排多少条

这个参数控制的是：

**融合完成后，最多拿前多少条文档送给 Cross-Encoder。**

它直接决定后面精排模型的负载。

如果这个值太小：

- 可能还没来得及把真正好文档送进精排，就在前面被截断了

如果这个值太大：

- Cross-Encoder 的延迟和成本会上升得很明显

实践里常见的范围是：

- `20 ~ 50`

如果是问答型 RAG，最终只给 LLM 喂 `3 ~ 5` 条证据，那么精排窗口通常不需要特别大。  
很多团队会先从 `30` 左右开始，再根据评测结果往上或往下调。

### 10.4.1 一个保守的默认参数组合

如果你现在没有历史评测数据，可以先从一个偏保守的默认值起步：

```jsonc
{
  "knn": {
    "k": 50,                  // 向量路先返回 50 条
    "num_candidates": 200     // 先粗看 200 条候选，再选出 top-50
  },
  "rrf": {
    "rank_window_size": 50    // BM25 路和向量路各取前 50 条参与融合
  },
  "reranker": {
    "rank_window_size": 30    // 最终只送 30 条给 Cross-Encoder 精排
  }
}
```

这个组合的思路是：

- 先保证两路召回都有一定覆盖
- 再把候选规模控制在 Cross-Encoder 能接受的范围
- 最后从精排结果里选前 `3 ~ 5` 条送给 LLM

### 10.4.2 最后不要凭感觉调参数

这些参数没有脱离业务场景的“万能最优值”。

更稳的做法是分 3 层看指标：

1. 召回层：看 top-k 召回率是否上来了
2. 重排层：看 rerank 后 top-3 / top-5 命中是否更稳
3. 系统层：看整体延迟、GPU 成本、QPS 是否还能接受

如果只看最终答案好不好，而不拆开看召回和重排，后面会很难知道到底该调 `k`、`num_candidates`，还是该调 rerank 窗口。

### 10.5 一个很实用的工程判断

如果你问“默认怎么做更稳”，我会给这个建议：

1. 先把 `BM25 + Vector + RRF` 放进 Elasticsearch
2. 候选池控制在 top-20 到 top-50
3. 再决定 Cross-Encoder 是放在 Elasticsearch inference 里，还是放在外部模型服务里

这样做的好处是：

- 前半段检索链路统一
- 候选池大小可控
- 后半段模型服务可以独立演进

这比一开始就在应用层拼很多临时逻辑更稳，也更适合后续排查和扩展。

### 10.6 业界常见的 Cross-Encoder 模型

从 Elasticsearch 官方支持和业界常见实践看，模型选择大致有 4 类：

#### 10.6.1 Elastic 官方模型

如果你已经深度使用 Elasticsearch，最直接的是官方的 `Elastic Rerank`。

它的特点是：

- 官方内置支持
- 面向 rerank 场景
- 接入 Elasticsearch inference API 比较顺

适合：

- 想快速跑通
- 不想先自建模型推理链路
- 希望检索和 rerank 尽量都在 Elastic 体系里完成

#### 10.6.2 Elastic 预配置接入的 Jina Reranker

Elastic 官方文档当前也推荐使用预配置的 `.jina-reranker-v3` endpoint。

这类方案的特点是：

- 直接走 Elastic 提供的集成能力
- 上手成本低
- 适合先建立生产基线

如果你的目标是先把“混合检索 + rerank”主链路稳定起来，它是很合理的起点。

#### 10.6.3 Cohere Rerank

如果你接受外部 API 依赖，`Cohere Rerank` 也是很常见的生产选择。

它的特点是：

- 专门做 rerank
- API 形态成熟
- 和 Elasticsearch inference endpoint 可以对接

适合：

- 不想自己托管模型
- 更在意接入速度
- 接受外部服务成本和网络依赖

#### 10.6.4 自托管 Hugging Face / 开源 Cross-Encoder

如果你更在意私有化、成本可控、模型自主权，常见做法是自己托管开源 reranker。

常见代表包括：

- `BAAI/bge-reranker` 系列
- `BAAI/bge-reranker-v2-m3`
- 其他支持 `text_similarity` / rerank 的 cross-encoder

这类方案适合：

- 有 GPU 资源
- 想做私有部署
- 需要和业务领域做更深适配

但代价也更明确：

- 你要自己承担部署、扩缩容、监控、超时控制
- 还要处理版本升级和模型切换

常见开源方向里，值得优先关注的通常有：

- `BAAI/bge-reranker-base`
- `BAAI/bge-reranker-v2-m3`
- `cross-encoder/ms-marco-MiniLM-L-6-v2`

它们分别更偏向：

- `bge-reranker`：中文和多语言场景里讨论度较高
- `bge-reranker-v2-m3`：更偏多语言和长文本能力
- `ms-marco-MiniLM`：英文信息检索社区里非常经典，体量相对轻

如果你的业务以中文为主，通常会先看 `bge-reranker` 系列。  
如果你更看重 Elastic 官方集成顺滑度，则更适合先从 `Elastic Rerank` 或 `.jina-reranker-v3` 起步。

### 10.7 怎么选模型，不要只看“谁最强”

生产里选 Cross-Encoder，我更建议看下面 5 个维度：

1. 中文和多语言效果
2. 单次 rerank 延迟
3. 候选池大小下的吞吐
4. 是否必须私有化
5. 是否容易接入你当前的 Elasticsearch / 推理基础设施

一个很实用的经验是：

- 如果你还在搭第一版，先用 Elastic 原生支持最顺的模型把链路跑通
- 如果你已经确认 rerank 是关键收益点，再考虑换更强或更适合中文的模型

不要一开始就陷入“模型榜单焦虑”。  
生产系统里，`候选池质量 + 时延预算 + 运维复杂度` 往往和模型本身同样重要。

### 10.8 一个推荐的默认落地方案

如果你现在要做一个保守而靠谱的企业 RAG 检索链路，我建议先从这个默认方案开始：

1. 文档切分后，建立 BM25 索引和 dense vector 索引
2. 查询时在 Elasticsearch 中同时跑 lexical 和 kNN
3. 用 `RRF` 融合两路结果
4. 把候选池控制在 top-30 左右
5. 用一个 Cross-Encoder reranker 做最终精排
6. 只把 top-3 到 top-5 证据送给 LLM
7. 对 top-k 召回、rerank 后 top-3 命中率、最终答案正确率分别评测

这条链路的优点不是“最先进”，而是：

- 工程边界清楚
- 容易排查问题
- 后续既能往 Elastic 内部收，也能往外部模型服务扩

## 11. 重排序常见误区

### 11.1 误区一：加了 Rerank 就一定变好

不一定。如果召回阶段已经漏掉真正相关内容，重排也无能为力。

### 11.2 误区二：Rerank 可以替代 query 理解

不能。用户问题如果表达含糊、简称很多、实体未补全，重排只能在已有候选中排序，无法完全替代查询改写和路由。

### 11.3 误区三：所有候选都值得重排

如果召回候选过多，重排成本和延迟会明显增加。通常先选一个合理候选池大小，再做精排。

### 11.4 误区四：做了混合检索，就不再需要重排

这也不对。混合检索通常提高的是候选覆盖，不自动保证前几名排序最优。

### 11.5 误区五：RRF 和 Cross-Encoder 是替代关系

很多时候它们更像前后衔接关系，而不是单纯替代关系。

## 12. 一个实用的接入思路

一个典型流程可以这样设计：

1. 先用关键词检索、向量检索或混合检索拿到多路候选
2. 如果是多路召回，先做融合、去重和统一粗排
3. 把候选池收缩到一个合理规模，例如 top-20 或 top-50
4. 再用 Cross-Encoder 或其他深度重排模型逐条精排
5. 取最终前几条进入上下文
6. 如有需要，再结合元数据做少量规则修正

要特别注意的是，重排序的收益通常需要通过对比来验证：

- 没有 Rerank 时，top-3 是否经常不准
- 加上 Rerank 后，最终回答是否更稳
- 延迟和成本是否在可接受范围内

## 13. 练习题与思考方向

### 练习 1

如果 top-20 候选里已经包含正确答案，但模型仍然经常答错，这通常说明哪一层可能需要优化？

参考方向：

- 候选排序不对
- 上下文拼接顺序不对
- 旧版本内容排在前面

### 练习 2

为什么说混合检索解决的是“覆盖”，而重排序解决的是“前排精度”？

思考方向：

- 两者在目标函数上并不相同

### 练习 3

为什么很多系统会先用 RRF 再用 Cross-Encoder，而不是只选其中一个？

参考方向：

- 候选规模
- 计算成本
- 前几名精度要求

### 练习 4

在什么情况下，加很重的 Cross-Encoder 可能收益不大？

参考方向：

- 数据规模小
- 候选差异很明显
- 召回已经非常准
- 真正问题出在离线数据质量

## 14. 总结与下一步建议

重排序的核心价值可以用一句话概括：

**它不是帮你“找更多”，而是帮你“把最该给模型看的内容排到最前面”。**

如果再进一步补一句，更接近生产实践的说法会是：

**混合检索负责尽量别漏，融合负责先排稳，深度重排负责把前几名做准。**

这一步对最终答案质量往往非常敏感，尤其是在企业知识库、制度库、产品资料库这类文本相似度高的场景。
