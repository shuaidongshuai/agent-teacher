## 适用人群

这篇文档适合已经知道 Embedding 是什么，但到了真实项目里，不知道该如何选模型的人，尤其适合：

- 要做企业知识库问答的人
- 需要在效果、成本、延迟之间做平衡的人
- 需要考虑私有化、许可证和合规约束的人

## 学习目标

学完后，你应该能够：

1. 用工程视角而不是榜单视角来做 Embedding 选型
2. 快速筛掉不适合自己场景的模型
3. 根据语言、预算、部署方式和语料特点建立候选池
4. 设计一轮小而有效的内部评测

## 1. 这篇文档想解决什么问题

很多人在做 RAG 时，会把问题问成：

**“现在最强的 Embedding 模型是哪一个？”**

但真实项目里更有用的问题其实是：

- 我主要是中文，应该优先看谁
- 我预算有限，哪个模型性价比更高
- 我必须私有化部署，哪些开源模型值得先试
- 我的文档很长、PDF 很多、甚至有图片，普通文本模型还够不够

所以，Embedding 选型不是找一个“绝对第一”的模型，而是找一个：

**在你的语料、查询、预算、部署约束和系统链路下最合适的模型。**

---

## 2. 为什么 Embedding 选型不能只看排行榜

排行榜当然有价值，但它更多回答的是：

**“在公开测试集上的平均表现谁更强。”**

而你真正关心的是：

**“在我的业务数据上，谁更稳、更便宜、更容易落地。”**

只看排行榜容易踩 4 个坑：

- 排行榜以英文或多语种基准为主，不等于中文企业语料表现
- 评测任务往往偏通用检索，不等于你的 FAQ、制度、合同、代码库
- 高分模型未必适合你的时延和吞吐要求
- 排行榜通常不直接反映私有化、许可证、地域合规和维护成本

更合理的用法是：

**先用榜单缩小候选范围，再用自己的数据做最后判断。**

## 3. 先建立一个正确预期

### 3.1 Embedding 决定召回上限，但不是唯一因素

如果你的数据清洗差、切分差、标题丢失、元数据没设计好，再强的 Embedding 模型也救不回来。

### 3.2 更大的模型不一定更适合

更大的模型通常意味着：

- 更高的调用成本或推理成本
- 更高的延迟
- 更大的显存和部署压力
- 对小规模业务未必有足够大的收益

### 3.3 模型表现必须放到整条链路里看

某个模型在 `top-k` 召回上不一定第一，但如果配合重排后整体答案质量更高，它在系统层面就可能更优。

### 3.4 “可部署”本身就是选型结果的一部分

如果业务要求内网部署、数据不出域、许可证可商用，那么很多“公开最强”模型在第一轮就应该出局。

## 4. Embedding 选型先看哪 6 个维度

### 4.1 语言和语料分布

先问自己：

- 主要是中文、英文，还是中英混合
- 有没有很多缩写、产品名、内部术语
- 查询语言和文档语言是否一致

如果是中文企业知识库，就不能只看英文基准成绩。

### 4.2 领域适配程度

不同领域差异很大，例如：

- 法务合同
- 金融研究
- 医疗说明
- 技术文档
- 客服 FAQ

术语密集场景里，通用模型和领域模型可能差很多。

### 4.3 查询形态

用户查询可能是：

- 两三个关键词
- 一句自然语言问题
- 带条件约束的复杂问题
- 跨语言查询

短 query 场景尤其考验模型把短问题和长文档片段对齐的能力。

### 4.4 成本与吞吐

至少要估算 3 件事：

- 离线全量建库要花多少钱
- 日常增量更新要花多少钱
- 在线 query embedding 的峰值吞吐是否扛得住

### 4.5 部署、合规与许可证

这里经常一票否决：

- 能不能只用云 API
- 是否必须私有化
- 是否能接受非商用许可证
- 是否要满足数据驻留或内网隔离

### 4.6 与现有检索系统的兼容性

还要看：

- 向量维度会不会把存储成本拉高
- 现有向量库是否支持
- 是否方便灰度切换和回滚
- 是否需要同时支持文本、PDF、图片等多模态输入

## 5. 当前市面常用 Embedding 模型怎么分组看

截至 **2026-06-17**，实战里常见模型大致可以分成 4 组：

### 5.1 通用云 API 型

代表：

- OpenAI `text-embedding-3-small`
- OpenAI `text-embedding-3-large`
- Voyage `voyage-4-lite`
- Voyage `voyage-4`
- Cohere `embed-v4.0`

特点：

- 接入快，默认体验通常比较稳
- 不需要自己维护推理服务
- 适合先验证业务、快速上线
- 缺点是持续成本和数据出域约束

### 5.2 高性能开源文本型

代表：

- BAAI `bge-m3`
- Qwen `Qwen3-Embedding-0.6B / 4B / 8B`
- Jina `jina-embeddings-v5-text-small`
- Nomic `nomic-embed-text-v1.5`

特点：

- 可私有化，可做深度定制
- 更适合有算力、有平台能力的团队
- 真正成本从“按 token 计费”变成“GPU + 运维 + 评测”

### 5.3 长上下文或长文档友好型

代表：

- Qwen3 Embedding 系列
- Jina v5 text 系列
- Cohere `embed-v4.0`
- Voyage `voyage-4 / voyage-context-3`
- `bge-m3`

特点：

- 更适合长制度文档、长报告、长技术文档
- 但长上下文不是让你放弃切分，而是让切分策略更灵活

### 5.4 多模态或 PDF 检索型

代表：

- Cohere `embed-v4.0`
- Voyage multimodal 系列
- Jina omni 系列
- Qwen3-VL-Embedding 系列

特点：

- 当你的资料里有截图、图表、扫描 PDF、图文混排时更有价值
- 如果你的数据几乎全是纯文本，优先级通常没那么高

## 6. 主流模型实战对比表

下面这张表不追求列全所有模型，而是优先覆盖：

- 团队最常见的采购与技术选型对象
- 能代表主要决策分支的模型
- 适合用来做第一轮候选池筛选的模型

> 注意：表里的“成本”是实战判断视角，不等于严格报价。  
> 云 API 更适合看公开单价；开源模型更适合看推理资源、部署复杂度和许可证约束。

| 模型 | 类型 | 典型优势 | 典型短板 | 更适合什么场景 |
| --- | --- | --- | --- | --- |
| `text-embedding-3-small` | 云 API，通用文本 | 成本低、接入简单、默认表现稳，通常适合做第一版基线 | 私有化不方便，极致效果不如更大模型 | 通用知识库、MVP、预算敏感项目 |
| `text-embedding-3-large` | 云 API，通用文本 | 效果更强，多语种能力稳，支持缩维后兼顾质量和存储 | 单价明显更高 | 召回质量更敏感、预算充足的通用检索 |
| `voyage-4-lite` | 云 API，通用文本 | 成本和延迟友好，适合高并发检索 | 极限效果弱于更强型号 | 大规模在线检索、成本敏感场景 |
| `voyage-4` | 云 API，通用文本 | 通用检索质量强，维度和输出类型可调 | 仍然是云 API 依赖 | 对效果要求较高的生产 RAG |
| `embed-v4.0` | 云 API / 企业部署，多模态 | 文本、图片、PDF 一体化，企业部署友好，长上下文强 | 如果只做纯文本检索，能力可能用不满 | 企业文档库、图文混排知识库、合规要求较高的团队 |
| `bge-m3` | 开源，多语种文本 | 社区成熟，支持长文本、多语种，还覆盖 dense/sparse/colbert 统一路线 | 真正落地需要自己处理推理、量化、吞吐和版本管理 | 私有化中文/多语种知识库，想保留检索方案灵活性 |
| `Qwen3-Embedding-0.6B` | 开源，多语种文本 | 体积相对小，中文与多语种兼顾，长上下文友好 | 绝对效果通常不如更大尺寸 | 私有化入门版、资源受限团队 |
| `Qwen3-Embedding-4B / 8B` | 开源，多语种文本 | 中文、跨语种、代码检索都值得重点关注，长上下文强，上限高 | 部署成本、显存压力和延迟更高 | 对中文效果要求高、能接受较重部署的团队 |
| `jina-embeddings-v5-text-small` | 开源，多语种文本 | 小模型里效果强，32K 上下文，支持 Matryoshka 截断，生产导向明显 | 许可证和商用边界要提前确认 | 想私有化，又希望兼顾效率与效果的团队 |
| `nomic-embed-text-v1.5` | 开源，长文本文本 | 可缩维、长上下文、部署生态友好 | 中文和企业中文术语场景通常不是第一优先 | 英文或混合语料、重视向量压缩和存储成本的场景 |

### 6.1 如果你只想记最重要的结论

可以先这样记：

- **云 API 低成本基线**：先看 `text-embedding-3-small`、`voyage-4-lite`
- **云 API 效果优先**：先看 `text-embedding-3-large`、`voyage-4`
- **企业文档 / PDF / 图文混排**：先看 `embed-v4.0`
- **中文私有化**：先看 `Qwen3-Embedding`、`bge-m3`
- **私有化且想要小模型性价比**：先看 `jina-embeddings-v5-text-small`

### 6.2 这些模型真正差在哪

很多团队看一堆榜单后还是不会选，是因为真正的差异不在一句“谁分数更高”，而在下面这些工程问题：

#### 差异 1：你是在买效果，还是买可用性

- OpenAI、Voyage、Cohere 的优势通常是“马上能用”
- 开源模型的优势通常是“可控、可私有化、可长期优化”

#### 差异 2：你是在买模型，还是买整套部署复杂度

- 云 API 的成本主要是 token 费用
- 开源模型的成本主要是 GPU、服务稳定性、吞吐优化、运维和评测

#### 差异 3：你是在做纯文本检索，还是复杂文档检索

- 纯文本知识库没必要过早追多模态
- 有扫描 PDF、表格截图、图文混排时，多模态 Embedding 的价值才会显著增加

#### 差异 4：你是否真的需要“大模型级 Embedding”

如果你的数据量不大、问题类型稳定、后面还有重排模型，`small` 或中小尺寸开源模型往往已经够用。

## 7. 不同业务场景，优先看哪些模型

### 7.1 中文企业知识库问答

优先考虑：

- `Qwen3-Embedding-0.6B / 4B / 8B`
- `bge-m3`
- `text-embedding-3-small`
- `text-embedding-3-large`

原因：

- 中文和企业内部术语通常比公开英文基准更关键
- 如果能上私有化，Qwen3 和 BGE 更值得优先试
- 如果想先快速验证业务，OpenAI 系列适合拿来做对照基线

### 7.2 预算有限、先做 MVP

优先考虑：

- `text-embedding-3-small`
- `voyage-4-lite`
- `Qwen3-Embedding-0.6B`
- `jina-embeddings-v5-text-small`

原因：

- 这类项目最怕一开始就把系统成本做高
- 更合理的策略通常是先做便宜基线，再证明高阶模型值得升级

### 7.3 必须私有化、数据不能出域

优先考虑：

- `Qwen3-Embedding`
- `bge-m3`
- `jina-embeddings-v5-text-small`
- `nomic-embed-text-v1.5`

额外注意：

- 不只看模型本身，还要看许可证是否允许商用
- 要提前评估量化、推理框架、GPU 占用、升级策略

### 7.4 文档很长，或者经常处理制度、规范、研报

优先考虑：

- `Qwen3-Embedding`
- `jina-embeddings-v5-text-small`
- `embed-v4.0`
- `voyage-4`
- `bge-m3`

原因：

- 长上下文能力更适合长段落建模
- 但仍然建议保留分块，不要把“长上下文”理解成“整篇文档直接一把塞进去”

### 7.5 图文混排、截图 PDF、文档页面检索

优先考虑：

- `embed-v4.0`
- Voyage multimodal 系列
- Jina omni 系列
- Qwen3-VL-Embedding 系列

原因：

- 这已经不再是普通文本 Embedding 的问题
- 如果你硬把复杂 PDF 先 OCR 再纯文本化，信息损失可能很明显

### 7.6 代码检索或技术文档检索

优先考虑：

- `Qwen3-Embedding`
- Voyage `voyage-code-3`
- `text-embedding-3-small / large`

原因：

- 代码检索和自然语言 FAQ 不完全一样
- 模型是否能同时理解代码 token、函数名、注释和自然语言问题会更重要

## 8. 一个更实用的选型流程

很多团队的问题不是不会查资料，而是候选模型太多，不知道怎么缩圈。

你可以按下面这个顺序做。

### 第 1 步：先做“一票否决”

先把这些问题回答掉：

- 数据能不能出域
- 是否必须私有化
- 是否允许非商用许可证
- 是否需要多模态
- 查询主要是不是中文

这一步做完，候选池通常能从十几个模型缩到 3 到 5 个。

### 第 2 步：再做“工程预算过滤”

继续问：

- 能接受云 API 的长期调用费吗
- 能接受自建推理服务吗
- 向量维度太高会不会把存储成本打爆
- 查询峰值下是否需要极低延迟

### 第 3 步：准备真实评测集

建议至少准备：

- 50 到 200 个真实用户问题
- 每个问题对应的标准命中文档或标准答案
- 覆盖短 query、长 query、术语查询、模糊问法、别名问法

最差的做法是只拿自己手写的“理想问题”去测。

### 第 4 步：统一其他变量

做模型评测时，尽量保持下面这些不变：

- 同一批清洗后的数据
- 同一套切分策略
- 同一套向量库配置
- 同一个 `top-k`
- 同一套重排策略

否则你以为在比模型，实际上可能在比切分方案。

### 第 5 步：看 4 类指标，而不是只看一个分数

建议至少看：

1. 检索指标：`Recall@k`、`MRR`、命中文档位置
2. 业务指标：最终答案是否可用、是否引用对文档
3. 工程指标：延迟、吞吐、重建索引耗时
4. 成本指标：建库成本、日常更新成本、在线查询成本

### 第 6 步：最后才做升级判断

如果 `small` 模型已经满足业务目标，就不要因为“榜单更强”而立即升级。

更合理的策略是：

- 先用便宜模型把数据、切分、召回链路做对
- 再用更强模型验证是否带来可感知提升
- 最后才决定是否值得切换

## 9. 常见误区、练习题与下一步建议

### 9.1 常见误区

#### 误区 1：只看“榜单第一”

榜单第一不等于你的业务第一。

#### 误区 2：一开始就追最大模型

很多时候先把数据和切分做好，收益比直接换大模型更大。

#### 误区 3：拿脏数据测模型

数据清洗差会让模型对比结果失真。

#### 误区 4：只看召回，不看最终回答

系统目标是回答质量，而不是某个中间指标漂亮。

#### 误区 5：忽略许可证和私有化边界

有些模型“技术上可跑”，但“业务上未必能用”。

### 9.2 练习题

#### 练习 1

你的公司要做中文内部知识库，数据不能出域，预算一般，第一轮你会优先挑哪 3 个模型做对比？

参考思路：

- 先从 `Qwen3-Embedding`、`bge-m3`、`jina-embeddings-v5-text-small` 起步
- 如果允许拿云 API 做基线，再加一个 `text-embedding-3-small`

#### 练习 2

如果 `text-embedding-3-large` 的召回比 `text-embedding-3-small` 高一点，但总体成本高很多，你会不会换？

参考思路：

- 看最终答案提升是否显著
- 看重排后差距是否还存在
- 看增长的成本是否值得

#### 练习 3

如果业务里大量是图文混排 PDF，为什么不能只拿纯文本 Embedding 做判断？

参考思路：

- OCR 后信息可能丢失
- 页面结构、图表和截图语义可能无法完整保留
- 多模态检索的收益在这类场景更明显

### 9.3 总结

Embedding 选型最重要的不是背下“现在谁最强”，而是建立下面这套判断顺序：

1. 先看数据能不能出域
2. 再看语言、领域和查询形态
3. 再看成本、延迟和部署复杂度
4. 最后用真实业务样本做内部评测

如果你只想要一句最务实的建议，可以记住：

**先用便宜、容易接入的模型做可靠基线，再决定是否值得为更强模型付出更多成本。**
