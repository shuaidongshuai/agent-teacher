## 1. 这篇文档讲什么

很多人做 RAG 时，把注意力放在知识库内容上，却忽略了另一件同样重要的事：

**系统是否真的理解了用户在问什么。**

用户的一句自然语言问题，常常并不适合直接拿去检索，因为里面可能有：

- 省略
- 代词
- 简称
- 别名
- 时间范围
- 条件约束

查询理解要做的，就是把“用户说的话”转成“系统更适合检索的话”。

---

## 2. 为什么用户原始问题不能直接拿去检索

看几个典型例子：

- “这个政策现在还能用吗？”
- “P8 出差去深圳住酒店标准是多少？”
- “企业版那个新套餐支持私有化吗？”

这些问题里都存在检索难点：

- “这个政策”到底指哪份制度
- “P8”是不是员工等级实体
- “深圳”是不是地区过滤条件
- “企业版那个新套餐”是不是产品别名

如果系统不先做理解，直接把原句拿去向量检索，结果可能“方向差不多”，但并不稳定。

---

## 3. 什么是查询理解

查询理解可以理解成线上检索前的一层语义加工。它的目标通常包括：

1. 识别关键实体
2. 补全隐含条件
3. 把口语表达改写成更规范的查询
4. 判断应该走哪种检索策略

它不是为了把问题“改得更好看”，而是为了让检索模块拿到更适合工作的输入。

---

## 4. 实体提取在 RAG 里有什么用

### 4.1 什么叫实体

在企业场景里，实体可能包括：

- 产品名
- 部门名
- 员工级别
- 城市
- 日期
- 版本号
- 客户类型
- 制度名称

### 4.2 实体提取的价值

实体提取常见的价值有三类：

#### 一是做过滤

例如识别出“深圳”“P8”“2025 版”之后，就可以在检索时加元数据过滤。

#### 二是做别名归一

例如用户说“企微”“企业微信”“WeCom”，系统可以统一映射到同一实体。

#### 三是做上下文补全

如果系统知道“P8”是员工职级，“差旅标准”是制度主题，那么后续 query 改写和路由就会更稳。

## 5. 实体提取怎么落地：规则、NER 模型还是大模型

前面说的是“实体提取有用”，但工程上真正的问题是：

**到底怎么提？**

常见有三条路线。

### 5.1 方案一：词典 + 规则

这是企业里最常见的起步方案。

做法通常是：

- 准备实体词典，例如产品名、城市名、部门名、职级名、制度名
- 准备别名字典，例如“企微 -> 企业微信”“北上广深 -> 北京/上海/广州/深圳”
- 用正则或规则识别日期、版本号、工号、单号、城市编码

例如：

```text
用户问题：P8 去深圳出差住酒店标准是多少？

实体提取结果：
- 职级：P8
- 城市：深圳
- 主题：差旅/酒店标准
```

优点：

- 快
- 便宜
- 可控
- 很适合高精度字段

缺点：

- 维护成本会越来越高
- 对口语、错别字、复杂上下文不够鲁棒
- 很难处理跨句、省略和隐含实体

适合：

- 城市、日期、职级、订单号、合同号、版本号这类强结构化实体
- 业务术语比较稳定的内部系统

### 5.2 方案二：传统 NER / 小模型序列标注

第二条路线是训练一个实体识别模型，例如：

- BiLSTM-CRF
- BERT + CRF
- RoBERTa / MacBERT 这类中文预训练模型做序列标注

它本质上是在做：

**给句子里的每个 token 打标签。**

例如：

```text
P8   -> B-LEVEL
去   -> O
深圳 -> B-CITY
出差 -> O
酒店标准 -> B-POLICY_TOPIC
```

优点：

- 比纯规则更能泛化
- 延迟通常低于大模型
- 适合高频稳定任务

缺点：

- 需要标注数据
- 实体标签体系要提前定义好
- 一旦实体类型经常变化，维护成本会上升

适合：

- 明确知道要抽哪些实体
- 每天请求量大，希望低延迟低成本
- 有能力积累标注集和持续训练

### 5.3 方案三：直接用大模型做结构化抽取

第三条路线是让 LLM 直接输出 JSON。

例如可以这样设计 prompt：

```json
{
  "product": "",
  "region": "",
  "city": "",
  "employee_level": "",
  "policy_topic": "",
  "time_range": "",
  "version": "",
  "need_clarification": false
}
```

对问题：

“今年华东企业版私有化报价政策还有吗？”

模型可能输出：

```json
{
  "product": "企业版",
  "region": "华东",
  "city": "",
  "employee_level": "",
  "policy_topic": "私有化报价政策",
  "time_range": "今年",
  "version": "",
  "need_clarification": false
}
```

优点：

- 开发快
- 对口语、省略、上下文补全更强
- 能一次抽取实体、意图和缺失槽位

缺点：

- 成本更高
- 延迟更高
- 输出稳定性不如规则和专用小模型

适合：

- 实体类型多、变化快
- 用户问题长且口语化
- 还在早期探索，需要先验证问题空间

### 5.4 怎么选

一个简单判断框架：

- 想先快速上线：先用词典 + 规则
- 流量大、实体稳定：补一个 NER 小模型
- 问题复杂、上下文强、变化快：优先用 LLM
- 真正的生产方案：往往是混合方案，而不是三选一

常见混合方式：

- 日期、编号、城市走规则
- 产品名、制度名走词典 + 别名库
- 隐含主题、缺失槽位、复杂上下文走 LLM

## 6. 为什么要做 Query 改写

很多用户问题天然更适合“交流”，但不一定更适合“检索”。

Query 改写常见目的包括：

- 把口语问题改成更规范的表达
- 展开简称和别名
- 把模糊代词替换成明确实体
- 拆成主问题和子问题
- 生成多个检索角度的 query

例如：

原问题：

“这个月华东还能按老政策走吗？”

可能改写为：

- “华东地区当前生效政策是什么”
- “华东地区旧政策是否仍然有效”
- “华东地区政策生效时间与版本变更”

这里的目标不是让模型写得更漂亮，而是让检索覆盖更多正确候选。

## 7. Query 改写怎么落地：从模板到 LLM

Query 改写也不是只有一种做法。

### 7.1 方案一：模板化改写

这是最轻量的做法。根据实体和意图，套固定模板。

例如用户问题：

“这个月华东还能按老政策走吗？”

先识别出：

- 地区 = 华东
- 时间 = 这个月
- 主题 = 政策有效性
- 版本 = 老政策

然后套模板：

- “华东地区本月生效政策”
- “华东地区旧政策是否有效”
- “华东地区政策版本变更时间”

优点：

- 非常可控
- 适合高频标准问法
- 很容易做 A/B 测试

缺点：

- 模板覆盖有限
- 表达一复杂就容易改不准

### 7.2 方案二：小模型生成改写

可以用 T5、mT5、BART 这类 seq2seq 模型做 query rewrite。

本质上是：

- 输入原始问题
- 输出 1 到 N 条更适合检索的 query

优点：

- 比模板灵活
- 推理成本通常低于大模型
- 可以做领域微调

缺点：

- 需要训练数据
- 泛化不一定比高质量 LLM 更强

适合：

- 请求量大
- 业务领域稳定
- 已经积累了“原问题 -> 优质检索 query”样本

### 7.3 方案三：用 LLM 做多路改写

这是目前最常见的实战方案。让 LLM 一次输出 1 到 3 条检索 query，从不同角度覆盖问题。

仓库里的 [query_rewriter.py](/Users/chenmingdong01/Documents/AI/agent/07-项目实战/智能金融投研助手-RAG/app/query/query_rewriter.py) 就是这个思路：要求模型

- 展开口语表达
- 补全隐含条件
- 生成 1 到 3 个不同角度的 query

这种方式适合：

- 原问题很口语
- 单次问题有多个信息维度
- 希望混合检索阶段拿到更多候选

但要注意两个风险：

- 改写太多，噪声变大
- 改写太“聪明”，反而偏离原问题

### 7.4 Query 改写的工程原则

无论用哪种方法，都建议遵守下面几条：

1. 改写结果尽量短，不要写成长段自然语言
2. 最多 1 到 3 条，避免无限扩写
3. 保留原问题中的关键实体，不要随意替换
4. 改写后最好能记录 `rewrite_reason`
5. 如果问题本来就很精确，可以不改写

一个实用判断是：

**不是每个 query 都要改写，只有“原问题不适合检索”时才改。**

## 8. 检索路由是什么

不是所有 query 都该走同一条检索链路。

检索路由的意思是：

**根据问题类型，把 query 分发到更适合的检索方式。**

例如：

- 明确问编号、产品名、制度名时，更适合关键词或精确匹配
- 自然语言问句、更偏语义理解时，更适合向量检索
- 高价值问题可以走混合检索加重排
- 某些实体类问题还可以先查结构化数据库，再补文档检索

路由的价值在于，不让所有问题都走“同一把锤子”。

---

## 9. 检索路由怎么落地：规则路由、分类模型、LLM Router

检索路由的核心问题是：

**这次查询到底该走 BM25、向量检索、混合检索，还是先查结构化库？**

### 9.1 方案一：规则路由

最常见的规则有：

- 命中编号、产品 SKU、制度编号 -> 走关键词检索
- 问“是什么、区别、原因、影响” -> 走向量或混合检索
- 带城市、时间、等级等过滤条件 -> 先做 metadata filter
- 问报表数值、库存、价格 -> 先查数据库，再补文档

优点：

- 简单、稳定、容易解释

缺点：

- 覆盖复杂场景能力有限

### 9.2 方案二：分类模型路由

可以把路由当成一个分类任务：

- 类别 A：关键词检索
- 类别 B：向量检索
- 类别 C：混合检索
- 类别 D：结构化查询 + 文档检索

可用模型包括：

- 轻量文本分类模型
- BERT 类别头微调
- Embedding + 线性分类器

优点：

- 比规则更能泛化
- 推理成本一般不高

缺点：

- 需要标注数据
- 类别边界容易随业务变化

### 9.3 方案三：LLM Router

让 LLM 直接判断：

- 需不需要检索
- 先检索什么
- 该走哪种策略

仓库里的 [nodes.py](/Users/chenmingdong01/Documents/AI/agent/07-项目实战/agent-agentic-rag/app/nodes.py) 已经体现了这种思路：

- `analyze_query` 先分析问题复杂度和初始 query
- `decide_retrieval` 再判断需不需要进入知识库
- `refine_query` 在检索不足时继续改写 query

这本质上就是一个轻量 Agent Router。

优点：

- 灵活
- 能利用上下文和中间结果
- 适合复杂多轮查询

缺点：

- 成本和时延更高
- 比规则更难稳定复现

### 9.4 路由选择建议

可以这样落地：

- FAQ、制度库、内部知识库早期：规则路由
- 有一定规模后：规则路由 + 分类模型
- 复杂分析型问题、Agentic RAG：LLM Router

很多团队最后会采用：

**规则兜底 + LLM 增强。**

也就是：

- 明确命中的场景，用规则直接处理
- 边界不清晰的场景，再交给模型判断

## 10. 一个常见的查询理解链路

可以把线上流程简化成下面几步：

1. 接收用户原始 query
2. 识别实体、时间、版本、地域、产品等关键信息
3. 做别名归一和必要补全
4. 生成一个或多个适合检索的 query
5. 判断走关键词检索、向量检索还是混合检索
6. 检索后进入重排序
7. 再把高质量候选交给生成模型回答

这个流程的关键思想是：

**线上检索不是一句 query 打到底，而是一次轻量的信息理解与调度。**

## 11. 一个可执行的实战方案

如果你现在就要在企业 RAG 里加“查询理解”，一个够实用的最小方案可以是下面这样。

### 11.1 第一步：先抽结构化槽位

先定义你最关心的字段：

- `entity`
- `alias`
- `time_range`
- `region`
- `version`
- `intent`
- `filters`

推荐做法：

- `time_range`、`version`、`region` 先用规则
- `entity`、`intent`、`missing_slot` 交给 LLM

示例输出：

```json
{
  "entity": "企业版",
  "time_range": "2025年",
  "region": "华东",
  "version": "老政策",
  "intent": "查询政策当前是否仍有效",
  "filters": {
    "region": "华东",
    "year": "2025"
  }
}
```

### 11.2 第二步：按问题类型生成检索 query

建议至少生成两类 query：

- 标准化 query：给 BM25 / Elasticsearch
- 语义化 query：给向量检索

例如：

原问题：

“华东企业版老政策现在还能用吗？”

可以生成：

- 关键词 query：`华东 企业版 老政策 生效 失效 版本`
- 语义 query：`2025年华东地区企业版历史政策是否仍然有效`

这一步的关键不是让两个 query 看起来不同，而是：

**让它们分别适合不同检索器。**

### 11.3 第三步：做路由决策

可以先写一个很朴素的路由器：

```python
def route_query(parsed):
    if parsed["intent"] in {"查编号", "查精确制度", "查版本"}:
        return "keyword"
    if parsed["filters"]:
        return "hybrid_with_filter"
    return "hybrid"
```

等规则不够用了，再升级成分类模型或 LLM Router。

### 11.4 第四步：把查询理解结果写进日志

很多团队把查询理解做了，但没有可观测性，最后很难排查问题。

建议至少记录：

- 原始 query
- 抽取出的实体和过滤条件
- 改写后的 query 列表
- 最终路由结果
- 检索命中文档数

这样一旦召回差，你就能知道问题出在：

- 实体没抽到
- 改写改偏了
- 路由选错了
- 检索器本身效果差

### 11.5 第五步：逐步升级，而不是一次做满

推荐迭代顺序：

1. 原始 query + 混合检索
2. 加实体抽取和 metadata filter
3. 加 1 到 2 条 Query 改写
4. 加规则路由
5. 再决定要不要上 LLM Router 或专用小模型

这个顺序的好处是：

- 每一步都能单独评估收益
- 不会一开始就把系统变得过重

## 12. 企业场景中的典型问题

### 12.1 简称和别名太多

同一个东西可能有：

- 正式名
- 内部简称
- 旧名字
- 销售叫法
- 用户口语叫法

如果不做归一，检索命中率会明显下降。

### 12.2 问题依赖上下文

用户会说：

- “这个”
- “上一版”
- “刚才那个产品”

这类 query 必须结合对话上下文做补全，否则几乎无法检索。

### 12.3 条件很多但表达不完整

例如：

- 地区
- 时间
- 版本
- 客户类型
- 员工级别

这些条件如果没有被识别出来，召回结果就容易“相关但不对”。

## 13. 常见误区

### 13.1 误区一：用户怎么问，就怎么检索

这在简单 FAQ 里可能还能工作，但在企业复杂场景里往往不够。

### 13.2 误区二：Query 改写越多越好

不是。改写太多会带来噪声、增加成本，还可能把原问题含义改偏。

### 13.3 误区三：实体提取只对结构化搜索有用

实际上，实体提取对文档检索也很重要，因为它能帮助做过滤、归一和排序增强。

### 13.4 误区四：一上来就应该全用深度学习模型

不是。很多强结构化实体，用规则更便宜、更稳定，也更容易解释。

### 13.5 误区五：查询理解可以完全替代高质量知识库

不能。查询理解只能优化“怎么问”，不能替代离线数据治理和高质量索引。

## 14. 练习题与思考方向

### 练习 1

为什么“这个政策现在还能用吗”不适合直接拿去检索？

参考方向：

- “这个政策”缺少明确实体
- “现在”包含时间语义
- “还能用吗”更像版本有效性判断

### 练习 2

实体提取和 Query 改写分别更像在解决什么问题？

思考方向：

- 实体提取更像识别关键条件
- Query 改写更像重写检索表达

### 练习 3

什么情况下应该把 query 路由到关键词检索而不是只走向量检索？

参考方向：

- 编号、产品名、专有名词明确
- 用户在找精确字段
- 术语必须精确命中

### 练习 4

如果你要做一个“差旅制度问答助手”，你会怎么选实体提取方案？

参考方向：

- 城市、职级、日期先用规则
- 制度主题可以用词典 + 别名库
- 复杂口语问题可以再加 LLM 抽取

### 练习 5

为什么很多生产系统不会一开始就用 LLM Router 处理所有请求？

参考方向：

- 成本和时延更高
- 输出稳定性不如规则
- 很多高频场景其实规则就够了

## 15. 总结与下一步建议

RAG 查询理解不是一个单点技巧，而是一组线上前处理能力：

- 实体提取，解决“条件识别”
- Query 改写，解决“检索表达”
- 检索路由，解决“该走哪条链路”

它们未必都要靠深度学习模型实现。

更准确地说：

- 强结构化字段，规则往往最好用
- 高频稳定任务，小模型很划算
- 复杂语义理解和多轮决策，大模型更有优势

真正的生产系统，通常不是“全规则”或“全 LLM”，而是：

**规则、专用模型和大模型的混合编排。**
