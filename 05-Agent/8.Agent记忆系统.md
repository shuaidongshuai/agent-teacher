## 1. 为什么 Agent 需要记忆

没有记忆的 Agent 有三个致命问题：

### 1.1 对话断裂

用户第 3 轮说"我之前提到的那个项目"，Agent 完全不知道在说什么。每轮对话都是独立的，没有上下文连续性。

### 1.2 Context window 爆炸

最直觉的解法是把所有历史消息都塞进 context。但 20 轮对话后，光历史就占了 8000+ token。模型的注意力被稀释，回答质量反而下降。

### 1.3 无法积累

用户上周告诉 Agent "我喜欢 Python"，今天再问"推荐一门语言"，Agent 还是不知道用户的偏好。

**记忆系统的核心价值：让 Agent 在有限的 context window 内，保持最大的信息利用率。**

## 2. 三层记忆模型

借鉴认知科学的三层记忆模型：

| 层级 | 类比 | 实现 | 主要职责 |
|------|------|------|----------|
| 短期记忆 | 工作台上的便签 | LLM 压缩摘要 + 最近消息 | 保持当前会话连续性 |
| 长期记忆 | 文件柜 | FAISS 向量索引 + JSON | 跨会话沉淀稳定信息 |
| 工作记忆 | 黑板上的任务清单 | 结构化 Dict / scratch pad | 维护当前任务状态 |

### 2.1 为什么需要三层

单层记忆不够用：

- 只有短期记忆：关掉就忘，无法跨会话积累
- 只有长期记忆：检索噪音大，缺少当前对话的连贯性
- 只有工作记忆：只能维持当前任务，记不住用户偏好和历史事实

三层协作才能同时满足"当前对话流畅"和"跨会话记住"。

### 2.2 三层的边界

很多 Demo 会把"历史消息""用户偏好""当前计划"都混在一起。生产里通常要先划边界：

- 短期记忆回答的是：`刚刚几轮我们在聊什么？`
- 工作记忆回答的是：`这次任务现在推进到哪一步了？`
- 长期记忆回答的是：`哪些信息过一段时间仍然值得被想起？`

这三个问题混了，系统就会出现两类坏现象：

- 不该长期保存的中间推理被写进长期记忆，后续检索被污染
- 本该及时丢弃的短期噪音一直带进 prompt，context 越来越脏

## 3. 生产级记忆治理：三层记忆到底怎么管

生产环境里，难点不是"有没有三层记忆"，而是"每一层怎么进、怎么出、怎么升级"。

### 3.1 一条经验先说清楚

**默认不升级，只有满足条件才升级。**

因为记忆系统最大的风险不是"记少了"，而是"记错了、记脏了、记爆了"。长期记忆一旦被污染，后续每次召回都可能把错误再次注入模型。

### 3.2 三层记忆的进入条件

| 层级 | 进入条件 | 不该进入的内容 |
|------|----------|----------------|
| 短期记忆 | 当前轮对话发生过，且短时间内仍可能被引用 | 已明确结束且无复用价值的闲聊 |
| 工作记忆 | 会影响当前任务推进的目标、约束、待确认项、已执行步骤 | 无法指导下一步行动的泛泛事实 |
| 长期记忆 | 跨轮次仍有价值，且相对稳定、可复用、可验证 | 一次性噪音、模型猜测、未经确认的中间结论 |

### 3.3 什么时候压缩短期记忆

短期记忆不是越长越好，生产里常见的触发器有三类：

1. `长度触发`
消息条数、token 数超过阈值就压缩。教学项目常用固定阈值，例如 `max_messages=20`、`keep_recent=6` 这种最小实现，但生产里更常见的是按 token 预算动态触发。

2. `阶段触发`
任务进入新阶段时压缩，比如"需求澄清结束，开始写方案"、"排障完成，开始修复"。这样摘要能按任务阶段沉淀，而不是机械按条数切。

3. `成本触发`
如果发现 prompt 中历史部分已经挤占了太多 token 预算，比如超过总预算的 30% 到 40%，就应该提前压缩，而不是等到彻底爆窗。

### 3.4 什么时候把某层记忆升级到下一层

这是最关键的问题。

#### 从短期记忆升级到长期记忆

满足下面任意两条，通常就值得考虑升级：

- `稳定`：不是一句临时抱怨，而是较稳定的偏好、身份、长期约束
- `复用`：未来多次任务中都可能用到
- `低争议`：用户明确说过，或能被外部系统验证
- `高价值`：遗漏后会明显影响后续体验或结果

适合升级的例子：

- "我主要用 Python 做实验"
- "我们的 RAG 系统主要服务金融投研分析师"
- "默认输出请用中文"

不适合升级的例子：

- "我今天心情一般"
- "先随便给我一个思路"
- "这一轮先试试 256 chunk size"

#### 从工作记忆升级到长期记忆

工作记忆里最容易被误写入长期的是中间过程。生产里更稳妥的规则是：

- `任务状态` 不直接升级
- `任务中沉淀出的稳定偏好、稳定约束、可复用经验` 才升级

例如：

- 工作记忆中的 `pending_questions=["用户使用什么 embedding 模型？"]`
  这是待确认问题，不该进长期记忆
- 工作记忆中的 `key_facts=["用户团队要求回答必须给出处"]`
  如果这个要求在多次任务里反复出现，就值得升级为长期偏好

#### 从短期记忆进入工作记忆

这一步往往比进入长期记忆更频繁。判断标准不是"值不值得以后记住"，而是"值不值得影响当前下一步动作"。

例如：

- 用户说："我现在要把召回率从 60% 提到 75%"
  这应该进入工作记忆的 `current_goal`
- 用户说："我们已经试过调 chunk size，但是没明显改善"
  这应该进入工作记忆的 `key_facts`
- 用户说："先别改代码，先给我排查思路"
  这应该进入工作记忆的任务约束

### 3.5 一个好用的升级判定公式

可以把一条候选记忆粗暴打分：

```text
记忆分 = 稳定性 + 复用性 + 业务价值 + 可验证性 - 时效性风险 - 歧义风险
```

当分数高于阈值时，才允许写入长期记忆。

这不是一定要真的写成数学公式，而是提醒你：**长期记忆的写入应该像数据库建索引，而不是像聊天记录备份。**

### 3.6 什么时候不该升级

以下内容建议明确禁止进入长期记忆：

- 模型自己的推测和补全
- 未经用户确认的推理结论
- 一次性任务状态
- 明显过期的信息
- 带隐私风险、但业务上没有必要保留的信息

### 3.7 冲突、过期和遗忘怎么处理

生产里不只是"写入"，还要治理旧记忆。

#### 冲突处理

如果用户今天说"我在北京工作"，下周又说"我已经搬到上海"，不能简单追加两条。

常见做法：

- 保留最新值，并给旧值打 `inactive` 或降低权重
- 给记忆加 `last_confirmed_at`
- 对互斥字段做单值约束，比如城市、岗位、默认语言

#### 过期处理

有些记忆天生有保质期：

- 临时项目目标
- 当前公司制度
- 本季度的业务指标

这类记忆应该加 TTL 或过期时间，过期后降权或删除。

#### 主动遗忘

长期记忆不是越多越强。常见清理动作：

- 合并相近重复条目
- 删除长期未命中的低价值记忆
- 对老旧但仍有参考价值的记忆只保留摘要，不保留全文

教学版实现通常只做最基础的近似去重。生产里通常还会继续加版本号、权重、命中次数、字段级冲突处理和过期机制。

## 4. 短期记忆压缩策略

### 4.1 问题：消息列表越来越长

每轮对话加 2 条消息（用户 + 助手）。10 轮就是 20 条，20 轮就是 40 条。

### 4.2 方案：LLM 摘要压缩

当消息数超过阈值（如 20 条），触发压缩：

```text
[msg_1, msg_2, ..., msg_14] → LLM 压缩 → 摘要文本（200字）
[msg_15, ..., msg_20] → 保留原文

最终 context = 摘要 + 最近 6 条消息
```

### 4.3 压缩 prompt 的设计要点

1. 保留关键信息：用户身份、偏好、讨论过的主题和结论
2. 保留未完成事项：待确认问题、未关闭的风险、明确约束
3. 去除闲聊和重复
4. 使用第三人称描述，减少歧义
5. 限制摘要长度，防止"压缩后反而越来越长"

### 4.4 压缩不是单纯摘要，而是信息重组

生产里更实用的压缩结果往往不是一段自然语言，而是半结构化摘要，例如：

```text
用户稳定偏好：
- 默认使用中文回答

当前讨论主题：
- 正在优化金融 RAG 系统召回率

已确认结论：
- 已尝试调整 chunk size，收益不明显

未完成问题：
- 尚未确认 embedding 模型
```

这样做的好处是后续更容易转入工作记忆或进入长期记忆筛选。

### 4.5 与 LangGraph MemorySaver 的区别

`MemorySaver` 是全量保存，每条消息都存储。适合消息量不大的场景。

LLM 压缩是有损保存，用摘要替代旧消息。适合长对话场景，但可能丢失细节。

所以生产里常见组合不是二选一，而是：

- 原始日志单独留存，用于审计和回放
- 运行时上下文使用压缩版短期记忆

### 4.6 摘要是临时现做，还是预先维护

生产里更常见的方式不是：

- 每来一个 query 就临时把全部历史重新总结一遍

也不是：

- 每条消息各自做一个独立摘要

更常见的是：**短期记忆内部预先维护一个滚动摘要。**

也就是说，短期记忆本身通常包含两部分：

```text
short_term_memory = {
  summary: "前面多轮对话的压缩结果",
  recent_messages: [...最近 N 条原始消息...]
}
```

它的更新流程通常是：

```text
新消息进入
→ 追加到 recent_messages
→ 检查是否超长
→ 如果超长，拿“旧摘要 + 即将被挤出的旧消息”做一次增量压缩
→ 更新 summary
→ recent_messages 只保留最近 N 条
```

所以 query 来的时候，系统通常直接加载：

- 已存在的 `summary`
- 最近 `N` 条原始消息

而不是临时再做一次全量摘要。

### 4.7 为什么通常不用“每个 query 临时摘要”

- 成本高：同一段历史会被反复总结
- 延迟高：每次都多一轮压缩调用
- 稳定性差：同样的历史，模型每次可能总结得不完全一样

因此，短期记忆里的摘要更像一个**滚动维护的会话摘要**，而不是 query 时临时生成的临时产物。

### 4.8 三种常见压缩模式

#### 滚动摘要

最常见。超过阈值就把旧消息批量压缩进 `summary`。

优点：

- 成本可控
- query 时延迟低
- 易于工程化

缺点：

- 如果压缩 prompt 设计不好，摘要会逐步漂移

#### 懒压缩

平时不压缩，只有在真正接近 token 上限时才压缩。

优点：

- 平均成本低

缺点：

- 触发那一轮延迟高
- 容易在高峰请求时抖动

#### 阶段摘要

不是纯按长度压缩，而是在任务阶段切换时做摘要，例如：

- 需求澄清结束
- 方案确定
- 排障完成

优点：

- 摘要更符合任务结构

缺点：

- 需要系统能识别阶段边界

## 5. 记忆存储选型：短期和长期一般存哪里

生产里一般不会把短期记忆和长期记忆都随便塞进同一类存储，因为它们的访问模式完全不同。

### 5.1 短期记忆一般怎么存

短期记忆服务的是当前会话连续性，核心要求是：

- 低延迟
- 可覆盖更新
- 容易按 session 读取

常见拆法是：

- `recent_messages`：内存、Redis、会话状态表
- `session_summary`：Redis、Postgres、MongoDB
- `working_memory`：Redis、状态表、graph state

如果系统是单机场景，短期记忆放进程内也能跑；一旦进入多实例部署，通常会外置到 Redis 或数据库。

### 5.2 长期记忆一般怎么存

长期记忆通常拆成两类：

#### 结构化长期记忆

比如：

- 用户身份
- 用户偏好
- 默认语言
- 长期约束

这类适合存：

- Postgres
- MySQL
- MongoDB

因为它们适合按字段更新、冲突覆盖、加 TTL、做审计。

#### 语义长期记忆

比如：

- 项目背景
- 历史任务经验
- 过去讨论过但难以字段化的稳定事实

这类适合存：

- pgvector
- Milvus
- Weaviate
- Pinecone
- Elasticsearch dense vector

### 5.3 生产里为什么通常是“双存储”

一个成熟系统往往不是“只用数据库”或“只用向量库”，而是两套并存：

- 能字段化的长期记忆，优先放结构化存储
- 需要语义召回的长期记忆，再放向量索引

原因是：

- 用户偏好、城市、默认格式这类字段，不值得只靠 embedding 找
- 纯向量存储不适合做强一致更新、冲突覆盖和字段治理

### 5.4 一个实用的最小组合

如果你刚开始做生产版，可以先记这个最小组合：

- 短期记忆：`Redis`
- 结构化长期记忆：`Postgres`
- 语义长期记忆：`pgvector` 或独立向量库

这样通常已经足够支撑大部分 Agent 记忆场景。

## 6. Query 进来后，怎么决定加载哪些记忆

这是记忆系统真正的路由层。

重点不是“能不能查到”，而是：

- 要不要加载短期记忆
- 要不要加载长期记忆
- 各自加载多少
- 加载哪一类

### 6.1 短期记忆通常主要靠规则控制

短期记忆和当前会话天然相关，所以通常不需要先跑一层复杂分类模型，再决定要不要查短期记忆。

更常见的是规则控制：

- 固定加载最近 `N` 条消息
- 如果超长，就加载 `summary + 最近 N 条`
- 如果当前有未完成任务，再加载对应 `working_memory`
- 如果 token 超预算，再缩减最近消息数量

所以短期记忆的核心问题一般不是：

- 要不要加载

而是：

- 加载多少
- 用什么窗口
- 是不是要带 working memory

### 6.2 长期记忆通常需要先做路由判断

长期记忆量大、噪音高、还可能过期，所以一般不会默认全查全带。

更常见的做法是，query 先过一层“是否需要长期记忆”的判断。

这层判断本质上就是一种 `query classification / routing`。

### 6.3 哪些 query 往往需要长期记忆

常见信号包括：

- 指代历史：`之前说过`、`上次那个`
- 偏好继承：`按我习惯`、`默认怎么做`
- 持续任务：`继续上次`、`还按原来的要求`
- 个性化决策：`适合我什么方案`
- 跨会话背景：`我那个项目`、`我们的系统`

如果 query 是一次性纯事实问题，例如：

- `Python 怎么读文件`

很多场景下就没必要查长期记忆，避免把无关背景带进 prompt。

### 6.4 长期记忆路由有三种常见做法

#### 纯规则

最便宜，也最容易上线。

例如命中某些表达就查长期记忆：

- `之前说过`
- `按我习惯`
- `继续上次`
- `我那个项目`

#### 轻量分类器

适合 query 量大、成本敏感的场景。

它输出的通常不是复杂标签，而是几个简单决策：

- 是否需要长期记忆
- 优先查哪类：`profile / preference / project / task_pattern`
- 召回 `top_k` 取多少

#### LLM 路由

最灵活，适合 query 复杂、表达不稳定的场景。

例如让模型输出：

```json
{
  "need_long_term_memory": true,
  "memory_types": ["preference", "project_context"],
  "reason": "用户在追问持续任务，并引用了个人偏好"
}
```

### 6.5 一种常见的生产级组合

很多系统不是一开始就上 LLM 路由，而是分层：

```text
query
→ 规则层决定短期记忆窗口
→ 轻量路由判断是否需要长期记忆
→ 若需要，再查结构化长期记忆 + 语义长期记忆
→ 做重排
→ 注入 prompt
```

这样的好处是：

- 短期记忆稳定、成本低
- 长期记忆避免无谓召回
- 复杂 query 才用更贵的路由能力

### 6.6 长期记忆不一定非得“先分类再检索”

还有一种常见做法是两阶段：

```text
query
→ 粗判断：要不要查长期记忆
→ 如果要，先各召回少量候选
→ 再用小模型或 LLM 做二次筛选
```

这种方式的优点是容错更高，因为“先严格分类再只查一类”有时会误杀。

### 6.7 最终注入通常长什么样

一个实用的注入组合通常是：

```text
短期记忆摘要
+ 最近 4~8 条消息
+ working memory
+ 结构化长期记忆 top 3
+ 语义长期记忆 top 3~5
```

这比“把所有历史都塞进去”稳得多，也更符合 token 预算控制。

## 7. 长期记忆的存储与检索

### 7.1 存储结构

最小可用结构通常至少包含：

`{content, category, timestamp, source_turn}`

在生产里，往往还会继续补：

- `confidence`：这条记忆有多可信
- `ttl` 或 `expires_at`：是否会过期
- `last_hit_at`：最近一次被召回是什么时候
- `hit_count`：被命中过多少次
- `status`：active / inactive / deleted

category 常见分类：

- `personal_info`：姓名、职业、所在城市
- `preference`：喜好、偏好
- `fact`：讨论过的稳定事实
- `constraint`：长期约束
- `task_pattern`：可复用的任务经验

### 7.2 存储流程

```text
每轮对话结束
→ LLM 提取候选记忆
→ 规则层做过滤 / 去重 / 冲突检查
→ 编码为向量
→ 存入 FAISS + JSON
```

关键不在"提取"，而在"提取后还要二次治理"。如果让 LLM 一把梭写入，长期记忆会很快脏掉。

### 7.3 检索流程

```text
新一轮对话开始
→ 用户输入编码
→ FAISS 语义检索
→ top-k 候选记忆
→ 规则重排（时间、新鲜度、类别、命中历史）
→ 注入 prompt
```

很多 Demo 到 FAISS top-k 就结束了，但生产里通常还会做一次重排：

- 用户当前问的是身份信息，优先 `personal_info`
- 当前是任务规划阶段，优先 `constraint` 和 `task_pattern`
- 很久没命中且已过期的记忆，降低权重

### 7.4 与 regex 提取的区别

`agent-chat-langgraph` 项目用正则表达式提取 facts，比如匹配"我叫 xxx""我住在 xxx"。

LLM 提取 + FAISS 检索的优势：

- 不需要预定义 pattern
- 能理解隐含信息
- 语义检索比精确匹配更灵活

劣势：

- 成本更高
- 提取质量依赖 LLM 能力
- 如果没有规则层兜底，容易写入噪音

## 8. 工作记忆的结构设计

### 8.1 什么是工作记忆

工作记忆是"当前任务的草稿纸"。它不是历史信息仓库，而是当前推理过程中的关键状态。

### 8.2 结构

```python
{
    "current_goal": "帮用户优化 RAG 召回率",
    "key_facts": ["用户在做金融投研助手", "当前召回率约60%", "已尝试调整chunk size"],
    "pending_questions": ["用户使用什么 embedding 模型？"],
    "reasoning_steps": ["建议先检查 embedding 质量", "再考虑混合检索"]
}
```

教学版通常也会采用类似结构，并限制字段数量，避免 scratch pad 无限膨胀。

### 8.3 生产里的工作记忆要点

1. `只保留行动相关信息`
能指导下一步动作的留下，不能指导行动的丢掉。

2. `不要把完整推理链永久保存`
很多中间推理只是暂时假设，不应该被当成事实反复注入。

3. `要有重置机制`
任务切换、阶段完成、人工接管时，工作记忆应该局部或整体清空。

### 8.4 注入方式

工作记忆通常以文本形式注入 system prompt。LLM 看到当前任务状态后，能更好地保持聚焦，不会"忘了在讨论什么"。

## 9. 教学版实现与生产版实现的差距

如果你回头看一个教学项目，发现它和上面的规则对不上，不要勉强解释成"它也算生产实践"。更合理的做法是明确差距。

### 9.1 教学版通常会省略什么

- 只按消息条数压缩，不按 token 预算压缩
- 只做向量检索，不做二次重排
- 只做简单去重，不做冲突更新
- 没有 TTL、过期、降权机制
- 没有 `confidence`、`hit_count`、`last_hit_at` 等治理字段
- 把记忆提取、过滤、写入放在同一个同步流程里

### 9.2 生产版通常要补什么

1. `写入前过滤层`
LLM 只负责提出候选记忆，最终是否写入要由规则层决定。

2. `冲突更新策略`
对于城市、岗位、偏好这类单值字段，要支持更新旧值而不是无限追加。

3. `过期与降权机制`
临时目标、阶段性状态、短期业务规则需要 TTL。

4. `检索后二次重排`
向量相似不代表业务相关，要结合类别、时效性和命中历史重排。

5. `可观测性`
要能看到记忆写入量、误召回率、过期命中率、压缩后的任务成功率变化。

### 9.3 如果项目实现不匹配，应该怎么改

优先按下面顺序改，而不是一次性推翻重写：

1. 先补 `memory metadata`
给长期记忆补 `confidence`、`status`、`expires_at`、`last_hit_at`。

2. 再补 `upgrade gate`
把"候选记忆提取"和"最终写入"拆开，中间加规则判定。

3. 再补 `retrieval rerank`
不要只看向量 top-k，把类别、时间、命中历史一起考虑。

4. 最后补 `lifecycle management`
增加 TTL、冲突更新、清理低价值记忆。

这样改造，成本可控，而且每一步都能单独验证收益。

## 10. 三层记忆流转样例

下面给一个更接近生产的样例。

### 10.1 场景

用户连续几轮对话：

1. "我在做一个金融投研 RAG 助手。"
2. "现在最大问题是召回率只有 60%。"
3. "我们已经试过调 chunk size，但提升不明显。"
4. "默认请用中文回答，而且给建议时尽量按排查优先级排序。"
5. "先别改代码，先帮我判断问题更可能出在召回、重排还是生成。"

### 10.2 这一轮里三层怎么落

#### 短期记忆

先完整保留以上几轮消息，因为它们都和当前对话连续性强相关。

#### 工作记忆

可以整理成：

```python
{
    "current_goal": "判断金融投研 RAG 助手召回率低的主要瓶颈",
    "key_facts": [
        "当前召回率约60%",
        "已尝试调整chunk size，效果不明显",
        "暂时不要直接改代码"
    ],
    "pending_questions": [
        "当前 embedding 模型是什么？",
        "是否已经接入 rerank？"
    ],
    "reasoning_steps": [
        "先区分问题主要在召回、重排还是生成",
        "优先检查召回链路"
    ]
}
```

#### 长期记忆

这一轮里适合进入长期记忆的，通常只有稳定偏好和长期背景：

- "用户在做金融投研 RAG 助手"
- "默认使用中文回答"
- "用户偏好按排查优先级组织建议"

而下面这些不适合直接进长期记忆：

- "当前召回率只有 60%"，因为它可能随着系统迭代很快过期
- "先别改代码"，因为这只是这一轮的任务约束

### 10.3 什么时候触发压缩

如果对话继续到 20 多条消息，短期记忆达到阈值，就把前面的消息压缩成摘要，只保留最近几条原文。

压缩后的摘要可能变成：

```text
用户正在做金融投研 RAG 助手优化。
当前核心问题是召回率偏低，之前已尝试调整 chunk size，但效果不明显。
用户偏好中文回答，并希望建议按排查优先级组织。
当前任务要求先定位问题层，再决定是否改代码。
```

### 10.4 什么时候升级到下一层

- 如果用户多次都要求"默认中文回答"，这条偏好应该稳定进入长期记忆
- 如果用户多次都在做同一套金融投研系统，这个项目背景也应该进入长期记忆
- 如果"按排查优先级排序"只在这一轮出现一次，可以先放短期记忆；如果后续多次重复，再升级到长期

这个例子反映的核心原则是：

**短期记忆保连续，工作记忆保推进，长期记忆保复用。**

## 11. 记忆与 LangGraph 的集成

### 11.1 图拓扑

```text
START → load_memory → chat → extract_and_store → compress_if_needed → END
```

### 11.2 各节点的记忆职责

| 节点 | 记忆操作 |
|------|---------|
| `load_memory` | 从长期记忆检索相关条目，注入 state |
| `chat` | 使用三层记忆构建 system prompt，调用 LLM |
| `extract_and_store` | 提取候选记忆，过滤后写入长期记忆，同时更新短期记忆 |
| `compress_if_needed` | 检查短期记忆是否需要压缩，必要时同步更新工作记忆 |

### 11.3 闭包模式

记忆对象（`ShortTermMemory`、`LongTermMemory`、`WorkingMemory`）通过 `make_nodes` 闭包注入，不存储在 state 中。这样 state 保持轻量级，记忆对象可以有复杂的内部状态。

### 11.4 为什么这个拓扑适合教学

教学项目通常会故意把记忆职责拆成几个清晰节点，便于理解：

- 先取回旧记忆
- 再让模型回答
- 然后决定要不要写入
- 最后决定要不要压缩

生产里可能会把"抽取候选记忆""过滤升级""冲突处理""压缩摘要"拆成更细的异步流程，甚至拆成在线路径和离线路径两套治理链路；这里的最小拓扑主要用于讲清主干思路。

## 12. 记忆系统的评测

### 9.1 记忆准确率

```text
记忆准确率 = Agent 正确回忆的信息数 / 用户告知的总信息数
```

测试方式：先告诉 Agent 多条信息，然后逐一询问"我之前说 xxx 是什么"。

### 9.2 记忆遗忘率

```text
遗忘率 = 压缩后丢失的关键信息数 / 压缩前的关键信息数
```

测试方式：进行 30+ 轮对话触发多次压缩，检查早期信息是否还能召回。

### 9.3 检索相关性

用 RAG 评测的指标（Recall@K、MRR）评估长期记忆的语义检索质量。

### 9.4 生产里还要看的指标

- `写入接受率`：候选记忆里最终被写入长期记忆的比例
- `冲突率`：新旧记忆发生冲突的比例
- `陈旧命中率`：被召回的记忆里有多少其实已经过期
- `误召回率`：召回内容与当前问题无关的比例
- `压缩后任务成功率变化`：压缩后任务完成质量是否下降

这些指标决定你是在"做记忆"，还是在"做幻觉放大器"。

## 13. 与人类记忆的类比

| 人类记忆 | Agent 记忆 | 相似点 |
|---------|-----------|--------|
| 感觉记忆 | 当前输入 | 极短暂，未经处理 |
| 短期/工作记忆 | 短期记忆 + 工作记忆 | 容量有限，需要主动维护 |
| 长期记忆 | 长期记忆 | 容量大，需要线索触发提取 |
| 遗忘曲线 | 压缩丢失 | 不重要的信息逐渐消失 |
| 记忆巩固 | 提取 + 存储 | 重要信息从短期转入长期 |

类比的价值是帮助理解设计决策，但不要过度类比。Agent 的记忆是工程系统，不需要也不应该完全模拟人类认知。

## 14. 常见误区

### 误区 1：什么都记

不加区分地记住所有信息，长期记忆膨胀，检索噪音增大。应该先做候选提取，再做升级判定。

### 误区 2：只用全量保存

把所有消息存在 context 里，不做压缩。20 轮后 context 爆满，回答质量下降。

### 误区 3：把任务状态当长期记忆

"这轮先别改代码""待确认 embedding 模型" 这些都属于工作记忆，不应该直接长期化。

### 误区 4：忽略检索质量

长期记忆存了很多，但检索时返回不相关内容，反而误导 LLM。记忆系统的价值取决于检索质量。

### 误区 5：不考虑成本和治理

三层记忆每轮可能增加多次 LLM 调用和检索开销。如果没有明确的写入规则、过期规则和观测指标，系统很快就会失控。

## 15. 练习题与思考方向

### 练习 1

运行 `agent-memory-enhanced` 项目的 `run_memory_demo.py`，观察 Agent 在多轮对话中的记忆行为。找出记忆成功和记忆失败的案例。

### 练习 2

修改 `app/prompts.py` 中的记忆提取 prompt，让它更严格，只提取个人信息和明确偏好，忽略一般性讨论。观察长期记忆的条目数变化。

### 练习 3

设计一个"记忆压力测试"：连续 30 轮对话，每轮告诉 Agent 一条不同的信息，然后在第 31 轮一次性询问所有信息。记录 Agent 的记忆准确率、误召回率和压缩后的遗忘率。

### 练习 4

思考：如果要给 `agent-agentic-rag` 项目添加记忆能力，你会如何定义：

1. 哪些信息只放工作记忆
2. 哪些信息可以升级到长期记忆
3. 哪些信息必须加 TTL

### 总结

三层记忆不是一个"加模块就行"的功能点，而是一套治理系统。

真正的生产难点不在于：

- 能不能存下来

而在于：

- 该不该存
- 存在哪一层
- 什么时候压缩
- 什么时候升级
- 什么时候删除或降权

如果你把这几个问题想清楚，记忆系统才真正从 Demo 走向生产。
