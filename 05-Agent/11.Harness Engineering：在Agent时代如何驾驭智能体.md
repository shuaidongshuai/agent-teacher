## 1. 适用人群

这篇文档适合以下读者：

- 已经理解 Agent、工具调用、状态管理基本概念，想进一步理解“人怎么驾驭 Agent 做开发”的人
- 已经用过 Cursor、Codex、Claude Code 之类工具，但感觉“能生成代码”和“能稳定交付”之间还有明显差距的人
- 想从“自己写代码”切换到“自己设计约束、让智能体持续产出”的工程师

## 2. 学习目标

读完后，你应该能够：

1. 说清楚 Harness Engineering 在 Agent 语境中的含义
2. 理解它为什么会从 Prompt Engineering、Context Engineering 继续演进出来
3. 区分“让 Agent 帮写一点代码”和“让 Agent 持续承担工程任务”的区别
4. 理解 Harness Engineering 的几个关键抓手：环境、约束、反馈、验证、协作
5. 判断一个 Agent 开发流程为什么容易失控，以及如何改造

## 3. 什么是 Harness Engineering

如果只看字面，`Harness` 有“马具、驾驭装置”的意思。放在 Agent 工程里，它强调的不是“AI 自动完成一切”，而是：

**人类负责设计系统和约束，智能体负责在这个系统中持续执行。**

所以，Harness Engineering 不是单纯的“AI 编程”，也不是“多写几个 Prompt”。它更接近一种新的开发范式：

- 人类主要负责定义目标、拆解问题、设计环境、设置边界、验收结果
- Agent 主要负责执行具体任务，例如写代码、补测试、改文档、跑检查、提 PR

用一句更直白的话说：

**Harness Engineering 关注的不是“怎么让 Agent 回答更好”，而是“怎么把 Agent 变成可驾驭、可复用、可验收的工程劳动力”。**

这也是为什么它常被描述为 `Agent-First` 的软件开发方式。开发者的重心，从逐行实现，转向了：

- 写清楚需求和成功标准
- 提供 Agent 可读的上下文与资料地图
- 构建可执行、可反馈、可验证的工作环境
- 审查和纠正 Agent 的输出

## 4. 它解决什么问题

很多人第一次使用 Agent 写代码，会经历一个很典型的阶段：

- 第一次看起来很惊艳
- 第二次开始出现偏题、误改、漏测
- 任务一长，Agent 就容易失去方向
- 项目一复杂，产出就变得难以维护

原因通常不是模型“完全不行”，而是缺少一个能驾驭它的工程系统。

Harness Engineering 试图解决的正是这些问题：

### 4.1 让 Agent 能持续工作，而不是只做一次性演示

Demo 阶段，你只要让它“这次成功”就够了。生产阶段，你需要的是：

- 每次都能在相近条件下稳定推进
- 出错时知道错在哪里
- 改完后知道有没有引入回归

### 4.2 让复杂项目对 Agent 更可理解

大型仓库最大的问题不是“代码太多”，而是：

- 背景分散
- 约束隐含
- 文档和代码脱节
- 依赖边界不清楚

如果这些东西对人都难理解，对 Agent 通常只会更难。

### 4.3 让人机协作从“碰运气”变成“有流程”

没有 Harness 时，开发者常常只能不断试：

- 换一个 Prompt
- 再解释一遍
- 再补一点上下文
- 失败后从头来过

Harness Engineering 要把这种随机试错，变成有结构的协作流程。

## 5. 核心概念和流程

结合文章里的核心观点，以及本项目已有的 Agent 学习脉络，可以把 Harness Engineering 拆成 5 个关键部分。

### 5.1 先把工程师角色从“实现者”切换成“指挥者”

在传统开发里，工程师主要亲自写实现；在 Harness Engineering 里，工程师更像是：

- 任务设计者
- 系统约束制定者
- 质量把关者
- 多个智能体或多轮执行的协调者

这并不意味着工程能力不重要。恰恰相反，它要求更强的：

- 需求抽象能力
- 系统设计能力
- 边界感
- 验证意识

因为如果你自己说不清楚要什么，Agent 只会更不清楚。

### 5.2 给 Agent 地图，而不是把所有资料一次性塞进去

文章里有一个很关键的观点：`AGENTS.md` 更像地图，而不是百科全书。

这背后的核心原则是：

- Agent 需要入口和路由
- Agent 需要知道去哪里找更细的资料
- Agent 不适合在一次上下文里吃下所有知识

在工程实践里，这通常表现为：

- 在仓库根目录提供简洁的 `AGENTS.md`
- 按主题拆分产品规范、架构文档、执行计划、参考资料
- 明确哪些文档是入口，哪些文档是细节展开

这和本项目的组织方式其实是同一个思路：先给学习地图，再给专题文档，而不是把所有概念压在一篇总文档里。

### 5.3 把系统做成适合 Agent 理解和操作的形状

Harness Engineering 很重要的一点，不是单纯“用 Agent 写代码”，而是：

**把代码库、工具链、观测方式改造成 Agent 更容易工作的样子。**

常见做法包括：

- 模块边界清晰，避免隐式耦合
- 分层结构稳定，便于 Agent 逐层定位
- 工具接口规范，输入输出明确
- 文档与目录命名一致，降低检索成本
- 通过 lint、结构测试、CI 把规则自动化

这本质上是在建设一个“Agent 友好型工程环境”。

### 5.4 建立反馈回路，而不是只看最终结果

Agent 最怕两种情况：

- 做错了但没人及时发现
- 做偏了但还在继续扩散

所以 Harness Engineering 不只关注最终交付，还关注中间反馈，例如：

- 是否跑通测试
- 是否违反架构约束
- 是否调用了错误工具
- 是否超出任务边界
- 是否引入安全风险

这里的关键不是“相信 Agent 会自我修正”，而是给它外部反馈回路。

一个典型闭环会是：

1. 人定义任务与成功标准
2. Agent 执行
3. 工具链返回结果与日志
4. 验证器、测试、审查机制指出问题
5. Agent 或人根据反馈继续修正

### 5.5 让验证机制独立于生成机制

Anthropic 的一个重要经验：与其让生成器自我表扬，不如设计一个独立、偏怀疑的评估角色。

这在 Agent 工程里非常重要，因为生成型系统常见问题是：

- 逻辑自洽，但事实错误
- 看上去完成了，实际上遗漏边界条件
- 自评过于乐观

因此，一个更可靠的方式是把角色拆开：

- Planner：负责任务拆解
- Generator：负责产出实现
- Evaluator：负责独立检查与批判

即使你不真的做成多 Agent，这个思想也依然成立：  
**生成和验收最好不是同一个心智回路。**

### 5.6 从 Prompt Engineering 演进到 Harness Engineering

可以把这条演进路线理解为：

1. `Prompt Engineering`
   重点是“怎么问”
2. `Context Engineering`
   重点是“给什么上下文”
3. `Harness Engineering`
   重点是“如何把上下文、工具、约束、验证、协作机制整体组织起来”

也就是说，Harness Engineering 并没有替代 Prompt 和 Context，而是把它们纳入更大的工程系统中。

### 5.7 在 Agent 项目里，最小可用 Harness 长什么样

如果你要在一个实际 Agent 项目里落地，不需要一开始就追求复杂平台。最小可用版本通常至少包括：

- 一份入口文档
  - 例如 `AGENTS.md`，说明项目结构、关键命令、重要约束
- 一套任务描述方式
  - 能把需求写成清晰的输入、边界和完成标准
- 一组可调用工具
  - 搜索、读写文件、运行测试、查看日志、调用服务
- 一套自动验证机制
  - 单测、集成测试、lint、类型检查、安全扫描
- 一种回归检查方式
  - 确认这次修改没有破坏旧能力

没有这些东西，Agent 再强，也更像一个偶尔高光的临时助手，而不是稳定协作的工程伙伴。

## 6. 常见误区或失败原因

### 6.1 误以为 Harness Engineering 等于“让 Agent 写更多代码”

这是最常见的误解。

Harness Engineering 的核心不是提高代码生成数量，而是提高：

- 任务可执行性
- 结果可验证性
- 过程可控性
- 系统可维护性

### 6.2 误以为文档越多越好

如果文档没有结构，或者入口不清楚，Agent 不会因为资料更多就更稳定。

更有效的做法是：

- 先给导航
- 再按主题拆分
- 让每份文档承担明确职责

### 6.3 误以为模型足够强，就不需要工程护栏

模型能力越强，越容易让人高估它的稳定性。真正导致生产事故的，往往不是模型“完全不会”，而是：

- 会做 80%，但剩下 20% 没被发现
- 大方向对，但细节持续偏
- 自信输出错误结论

所以越想依赖 Agent，越需要验证机制。

### 6.4 误以为多 Agent 一定更高级

多 Agent 只是组织方式，不是天然答案。

如果：

- 任务边界本来就不清楚
- 验证标准还没建立
- 工具链还不稳定

那你只是把一个混乱系统拆成了多个混乱角色。

### 6.5 误以为 Harness Engineering 只和代码生成有关

它其实覆盖更广，包括：

- 文档生成
- 测试生成
- 架构约束
- 观测与审查
- 工作流调度
- 人工兜底设计

本质上，它是“如何组织人和智能体协作做工程”的问题。

## 7. 练习题或实战建议

### 7.1 练习题

1. 如果一个 Agent 经常能完成简单任务，但一到跨文件修改就开始失控，问题更可能出在模型能力，还是出在工程 Harness？为什么？
2. 为什么说 `AGENTS.md` 更像地图，而不是百科全书？
3. 如果让同一个 Agent 既生成代码又自我验收，最容易出现什么偏差？

### 7.2 思考方向

参考答案可以从下面几个角度思考：

- 复杂任务失控，通常不只是“不会写”，更可能是上下文组织、边界约束、验证反馈不够
- 地图的作用是降低搜索成本、明确入口和路径，而不是一次性堆满细节
- 自生成自验收容易出现自我评估偏差，因此应增加独立验证角色或外部检查机制

### 7.3 一个很适合立刻做的小练习

你可以拿一个自己的 Agent 项目，补上下面 4 件事：

1. 新建或重写 `AGENTS.md`
2. 明确列出 3 条最重要的架构约束
3. 给一个常见任务写出“完成标准”
4. 把至少 1 个验证动作自动化，例如测试或 lint

做完后再让 Agent 执行同类任务，通常就会明显感觉到产出稳定性提升。

## 8. 总结与下一步建议

一句话总结：

**Harness Engineering 不是“让 AI 替你写代码”，而是“把项目改造成一个人能指挥、Agent 能稳定执行、结果还能被验证的工程系统”。**
