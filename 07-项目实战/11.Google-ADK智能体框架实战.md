## 2. 什么是 Google ADK

**ADK（Agent Development Kit）** 是 Google 在 2025 年开源的、**代码优先（code-first）** 的智能体开发框架，用来构建、评测、部署 AI Agent。它对 Gemini / Vertex AI 生态支持最顺，但不锁模型（可通过 LiteLLM 接 OpenAI、Anthropic、本地模型）。

一句话概括它的定位：

> **像写后端服务一样写 Agent**——用普通 Python 函数当工具，用清晰的对象组合多智能体，用内置的 Runner / Session / Eval / Web 调试台把"从 Demo 到上线"这条路铺好。

三个最能代表 ADK 风格的设计：

- **Agent 即对象**：`root_agent` 是一个约定入口变量，`adk web` / `adk run` 自动发现它。
- **Workflow Agent**：把"顺序、并行、循环"做成一等公民（`SequentialAgent` / `ParallelAgent` / `LoopAgent`），让你在"LLM 自主决策"和"确定性流程"之间自由取舍。
- **自带调试与评测**：`adk web` 可视化每一步事件、工具调用、state；`adk eval` 用评测集回归。

## 3. ADK 解决什么问题

自己手写 Agent 循环时，往往要反复造这些轮子：状态怎么在步骤间传、工具怎么描述给模型、多智能体怎么路由、怎么加护栏、怎么观测、怎么评测、怎么部署。ADK 把这些沉淀成了框架能力：

| 你想做的事 | 手写时的痛点 | ADK 的答案 |
|---|---|---|
| 让 Agent 调工具 | 手写 JSON schema、解析 tool_call | 直接传 Python 函数，自动生成 schema |
| 多步骤流程 | 手写状态机 / if-else 编排 | `SequentialAgent` / `ParallelAgent` / `LoopAgent` |
| 步骤间传数据 | 自己维护 dict 上下文 | `output_key` 写入 state，`{key}` 读入 |
| 多智能体协作 | 手写路由与消息传递 | `sub_agents` 委派 / `AgentTool` 调用 |
| 加安全护栏 | 到处插 if | 六类 callback 钩子 |
| 调试与观测 | 打印 log 猜执行路径 | `adk web` 可视化事件流 |
| 回归评测 | 自己攒脚本 | `adk eval` + 评测集 |

**和 LangGraph 的直觉对比**：LangGraph 把一切建模成"图 + 节点 + 边"，灵活但要自己画图；ADK 更"面向对象 + 约定优先"，常见编排（顺序/并行/循环）开箱即用，多智能体是它主推的方向。没有谁绝对更好，理解两套心智模型能帮你在项目里选型。

## 4. 核心概念全景

在动手前，先建立一张"地图"。ADK 的核心概念可归为 5 组：

**(1) Agent —— 干活的主体**

- `LlmAgent`（别名 `Agent`）：由大模型驱动，会推理、调工具、做决策。**四个关键字段**：
  - `name`：唯一标识（多智能体委派时用）；
  - `model`：驱动模型；
  - `instruction`：系统提示词（人设 + 行为准则）；
  - `description`：一句话"我能干嘛"——**父 Agent 靠它决定要不要把任务交给我**。
- Workflow Agent：`SequentialAgent`（顺序）、`ParallelAgent`（并行）、`LoopAgent`（循环）。它们**自己不调用 LLM**，只负责编排里面的子 Agent。

**(2) Tools —— Agent 的手脚**

- 函数工具：普通 Python 函数，**类型标注 + docstring 会被读成工具描述**，所以要写清楚。
- 内置工具：`google_search`、代码执行等（注意：内置工具通常要在一个 Agent 里"独占"）。
- `AgentTool`：把一个 Agent 包装成工具给别的 Agent 调用。

**(3) Session / State / Memory —— 上下文与记忆**

- `session.state`：本次会话的"共享内存"。`output_key` 把某个 Agent 的输出写进去，下一个 Agent 用 `instruction` 里的 `{key}` 读出来——**这是工作流传数据的核心机制**。
- Memory：跨会话的长期记忆（`InMemoryMemoryService` + `load_memory` 工具，或自己接数据库/向量库）。

**(4) Runner / Event —— 运行时**

- `Runner` 驱动一次执行，产出一串 **Event**（谁说了什么、调了什么工具、改了什么 state）。`adk web` 展示的就是这串事件。

**(5) Callbacks —— 切面钩子**

- 在"模型 / 工具 / Agent"执行的前后各有钩子。典型用法：`before_model_callback` 返回一个 `LlmResponse` 就能**拦截**本次模型调用（做输入护栏）。

## 6. 逐关卡讲解

下面每关只点出"核心概念 + 关键代码点 + 在 `adk web` 里该观察什么"。

**关卡 01 · LlmAgent 基础**：一个没有工具的纯对话 Agent。重点体会 `instruction`（人设）和 `description`（能力自述）的区别。观察：它遇到需要实时数据时会如实说"我没有工具"。

**关卡 02 · 函数工具**：写两个普通函数 `get_weather` / `get_current_time`，塞进 `tools=[...]`。重点：**docstring 和类型标注就是给模型看的工具说明书**。观察：`adk web` 里能看到 tool_call 的参数和返回。

**关卡 03 · 内置搜索**：`from google.adk.tools import google_search`。重点记住那条坑：**内置工具通常不能和自定义函数工具混在同一个 Agent**，要混用就用关卡 05 的 AgentTool 包一层。

**关卡 04 · 多智能体委派**：一个 `support_coordinator` 挂了两个专家 `sub_agents`（订单、账号）。重点：**委派是"控制权交出去"**，靠子 Agent 的 `description` 做路由。观察：问订单问题时，事件流里会出现 `transfer_to_agent`。

**关卡 05 · Agent 当工具**：用 `AgentTool(agent=translator)` 把翻译器、摘要器包成工具。重点：**AgentTool 是"叫它干一件事、结果拿回来"**，主 Agent 不交出控制权——和关卡 04 正好互补。

**关卡 06 · 顺序流 + state**：`SequentialAgent([outliner, drafter, polisher])`。重点：`outliner` 用 `output_key="key_points"` 写状态，`drafter` 用 `instruction="...{key_points}..."` 读状态。**这就是工作流传数据的标准姿势**。

**关卡 07 · 并行流**：`ParallelAgent([pros, cons, trend])` 三路同时跑，各写各的 key，外面再套 `SequentialAgent` 接一个 `synthesizer` 汇总。重点：并行分支的 `output_key` 必须互不相同，否则会互相覆盖。

**关卡 08 · 循环 + escalate**：`LoopAgent([critic, reviser], max_iterations=3)`。重点：`critic` 觉得够好就调用 `exit_loop` 工具，工具里 `tool_context.actions.escalate = True` 让循环停下；`max_iterations` 是防死循环的兜底。

**关卡 09 · 结构化输出**：给 `LlmAgent` 设 `output_schema=ReviewAnalysis`（一个 Pydantic 模型）。重点坑：**设了 `output_schema` 的 Agent 不能再用工具、也不能委派**，它只负责"把输入整理成指定结构"。

**关卡 10 · 回调护栏**：`before_model_callback` 检查用户输入，命中敏感词就返回一个 `LlmResponse` 直接拦截（不再调模型）；`before_tool_callback` 打印每次工具调用做审计。重点：**返回值决定"是否短路"**——返回对象=拦截，返回 `None`=放行。

**关卡 11 · 记忆**：工具函数声明 `tool_context: ToolContext` 形参后，ADK 会自动注入，借它读写 `state`（短期记忆）；同时把偏好写进本地 JSON 文件模拟跨会话的长期记忆。文末注释给出了 ADK 原生的 `InMemoryMemoryService + load_memory` 思路。

## 7. Capstone：AI 深度研究助手架构

`research_assistant/` 把前面的能力串成一条完整流水线，输入一个主题，自动产出并保存一份研究报告：

```
用户主题
   │
[规划] planner ─────────── output_schema(关卡09) + 输入护栏(关卡10)
   │  写 state["plan"]
[并行研究] ParallelAgent ── 并行(关卡07) + 函数工具 web_search(关卡02) + 工具日志(关卡10)
   ├ researcher_1 → finding_1
   ├ researcher_2 → finding_2
   └ researcher_3 → finding_3
   │
[撰写] writer ──────────── 读 {plan}/{finding_*}，写 state["draft"]（顺序流+state 关卡06）
   │
[评审循环] LoopAgent ────── 循环+escalate(关卡08)
   ├ critic  → 够好就 exit_loop
   └ reviser → 改稿覆盖 draft
   │
[定稿] finalizer ───────── 函数工具 save_report 落盘
   │
研究报告（保存到 research_assistant/output/）
```

顶层是一个 `SequentialAgent`，把这 5 个阶段按顺序编排。**它几乎覆盖了全部关卡的能力**，是理解"单点能力如何组合成系统"的关键样本。建议对照 [research_assistant/agent.py](/Users/chenmingdong01/Documents/AI/agent/07-项目实战/agent-google-adk/research_assistant/agent.py) 逐段读。

> 注意：为了离线也能跑通结构，`web_search` 是**模拟实现**，真实项目里换成 `google_search` 或你自己的检索接口即可。

## 9. 常见误区与失败原因

1. **关卡目录名用数字开头**（如 `01_agent`）：Python 包名不能以数字开头，`adk` 加载会失败。本项目用 `s01_...` 规避——这是个真实的坑。
2. **把内置工具和函数工具混用**：`google_search` 等内置工具通常要独占一个 Agent，混用会报错。需要混用时用 `AgentTool` 包成子 Agent。
3. **给 `output_schema` 的 Agent 还挂了工具**：两者互斥。结构化输出的 Agent 只做"整理成结构"，不能调工具/委派。
4. **并行分支共用同一个 `output_key`**：`ParallelAgent` 里的分支会互相覆盖状态，必须用不同的 key。
5. **循环忘了退出条件**：只写 `LoopAgent` 不给 `exit_loop`/`escalate`，就只能靠 `max_iterations` 硬停；两者要配合。
6. **`instruction` 里写了 `{xxx}` 但 state 里没有该 key**：模板替换会失败或拿到空值。确认上一步确实用 `output_key` 写了。
7. **只跑成功路径**：不看失败链路（工具报错、护栏拦截、委派路由错）就不算真的掌握。多在 `adk web` 里制造异常输入观察。
8. **description 写得含糊**：多智能体路由完全依赖它。`description` 不是给人看的注释，是给"父 Agent 做决策"的依据。

## 10. 实战练习题

按难度递增，建议动手改代码：

1. **（易）** 给关卡 02 再加一个 `get_exchange_rate(from, to)` 工具，让 Agent 能答汇率。
   *思路：仿照 `get_weather` 写函数 + 加进 `tools`，docstring 写清楚参数。*
2. **（易）** 把关卡 09 的 `ReviewAnalysis` 加一个字段 `main_issue: str`（用户最主要的不满点）。
   *思路：Pydantic 模型加字段 + `Field(description=...)`，模型会自动填。*
3. **（中）** 给 capstone 的 `researcher` 数量从 3 个改成"按计划里的子问题数动态生成"。
   *思路：`ParallelAgent` 的 `sub_agents` 是固定列表，动态数量需要自定义 Agent 或改成先让 planner 固定输出 N 个；先思考为什么固定列表不够灵活。*
4. **（中）** 把关卡 10 的护栏升级：命中敏感词时不是直接拒绝，而是**脱敏后**再放行给模型。
   *思路：`before_model_callback` 里改写 `llm_request.contents` 的文本，返回 `None` 继续。*
5. **（难）** 给 capstone 接**真实检索**：把 `web_search` 换成 ADK 内置 `google_search`。
   *思路：注意内置工具的独占约束——可能需要把"搜索"单独拆成一个用 `AgentTool` 包装的子 Agent。*
6. **（难）** 给 capstone 加**长期记忆**：记住用户偏好的报告风格（如"更技术/更通俗"），下次自动应用。
   *思路：结合关卡 11 的记忆工具 + 在 planner 的 instruction 里读入偏好。*

| 关卡 | 目录 | 学到什么 | 与前面哪一关对照 |
|---|---|---|---|
| 进阶01 | `adv_01_custom_agent` | 继承 `BaseAgent`、重写 `_run_async_impl`，写出**条件分支**等动态控制流 | 补上关卡 06/07 工作流"只能固定编排"的短板；也是 capstone 练习第 3 题的解法 |
| 进阶02 | `adv_02_mcp_tools` | 用 `MCPToolset` 接入 **MCP** 服务器（本例：文件系统） | 对比关卡 02 的进程内函数工具——MCP 工具来自独立服务、可复用整个生态 |
| 进阶03 | `adv_03_a2a` | **A2A 协议**：用 `to_a2a` 暴露服务端、`RemoteA2aAgent` 远程调用 | 对比关卡 04 的同进程委派——A2A 是跨进程/跨网络/跨框架 |
| 进阶04 | `adv_04_optimize` | **GEPA 提示词自动优化**（`adk optimize`）：给评测样本自动改写 instruction | 把"人工调 prompt"变成可度量的优化，衔接 `06-评测与优化` |

要点提示：

- **进阶01（自定义 Agent）最值得先做**——它才是"编排自由度"的天花板：`SmartRouterAgent` 先跑分类器，再**按 state 里的结果决定跑哪个分支**，这是 `SequentialAgent` 写不出来的。
- 进阶02 运行需要本机装 Node（`npx`）；进阶03 需要 `pip install a2a-sdk` 且要开两个终端（先服务端后消费端）；进阶04 需要 `pip install "google-adk[eval]"`，且真实运行会做多轮模型调用、消耗配额。
- 一句话记忆这 4 个能力覆盖的维度：**动态控制流（自定义 Agent）、工具生态（MCP）、Agent 互联（A2A）、自动调优（GEPA）**。再往外还有实时流式（`live`）、持久化 Session/Memory、Plugins 全局护栏、可观测性与部署等，属于"上线运维"层，可按需查官方文档深入。
